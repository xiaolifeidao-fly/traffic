# 实现每日汇总、差异预警与指定日期重跑

## 1. 任务目标

本任务仅完成「梳理需求」：在前置任务建立的 `reconciliation` 数据模型基础上，为 Phoenix Suffer 服务补齐一个可由启动流程托管的每日对账执行能力。该能力须在 **`Asia/Shanghai` 每日 00:10:00** 汇总前一自然日的人工维度、上游维度和系统账户状态，按默认 `5%` 阈值生成账户状态差异预警，并支持指定统计日期的串行、幂等重跑和可定位的执行日志。

本阶段只更新需求文档，不修改 `phoenix/` 下的业务代码、依赖或表结构。

## 3. 前置条件与范围边界

1. 本任务依赖 `reconciliation-backend-0d79cc3a4e` 和 `reconciliation-backend-f28aa210c5`。动作执行前必须确认前置任务实际提供 `reconciliation` Entity、Repository、配置/主体/日汇总/状态/预警表及其 DDL；如果前置代码未合入，本任务可以在同一变更中补齐缺失模型，但不得假设这些表已存在。
2. 人工维度的用户分层、订单状态映射、上游流水类型与金额符号、账户主体映射和系统欠款公式仍以已确认的业务字典为输入。缺少某日必需配置或映射时，该日期执行必须失败并记录原因，不能以零值补齐后写成成功汇总。
3. Phoenix 是新上游服务；本任务只读取 Phoenix 本地已同步的订单/账户/流水和新对账表，不变更 Kakrolot、Barry、`account_detail`、`order_record` 或 dashboard 的既有契约和统计语义。

## 4. 需交付的内容

### 4.1 对账执行服务与数据访问

动作执行在 `phoenix/server/suffer/service/reconciliation/` 增加日汇总服务（文件名可按现有命名调整，例如 `reconciliation_service.go`、`daily_summary_job.go`），复用前置任务的 Repository，并补充以下职责：

- `RunDailySummary(ctx, statDate, trigger)` 作为定时任务和人工重跑共享的唯一入口；`trigger` 至少区分 `SCHEDULED` 与 `MANUAL`，不允许两套计算代码分叉。
- 严格以 `Asia/Shanghai` 解析 `statDate`（`YYYY-MM-DD`），构造 `[当天 00:00:00, 次日 00:00:00)` 的查询窗口；自动调度日期为 `time.Now().In(shanghai).AddDate(0, 0, -1)`。
- 按已确认口径生成或更新 `ManualDailySummary`、`UpstreamDailySummary`、`SystemAccountStatusDaily`，再以同日人工账户状态计算 `AccountStatusDiffAlert`。日汇总、系统状态、预警均按前置任务定义的自然键 upsert，不能只依赖 GORM `Save` 的主键行为。
- 全部金额、比例、汇率及差异率使用 decimal 字符串或高精度 decimal 运算；禁止 `float64`。汇总行必须保存本次使用的配置和汇率快照，并写入非空 `calc_version`。
- 除执行日志状态更新外，同一统计日期的汇总、系统状态和预警写入应在一个数据库事务中完成；任一前置校验、来源查询或写入失败时回滚该次快照写入，并在事务外把失败详情落到执行日志。

### 4.2 调度器接入与生命周期

在 `phoenix/server/suffer/web-api/initialization/` 新增调度初始化能力，并由 `initialization.Init()` 在 DB 成功初始化后、路由启动前调用。实现要求：

- 使用可显式指定 Location 的 cron 实现；若新增第三方库，依赖仅加入实际使用的 Go module（预计为 `phoenix/server/suffer/web-api/go.mod`），不能放入无关模块。
- cron 表达式固定为每日 `00:10:00`，并显式传入 `Asia/Shanghai` Location；不能依赖服务器 `time.Local` 或容器时区。
- 初始化失败（例如时区加载、任务注册失败）应使 `web-api` 启动失败；任务单次执行失败只记录本次执行失败，不得终止 HTTP 服务或停止后续日程。
- 调度回调只负责计算目标日期并调用同一个 `RunDailySummary`；服务启动时**不补跑**昨天或历史日期，避免部署/重启触发非预期结算。补跑只能由指定日期接口触发。
- 应保留调度器实例供进程关闭时停止；如当前路由运行方式缺少 graceful shutdown 钩子，动作执行须将该限制明确写入代码日志，并避免重复 `Start()`。优先在不改变既有 `routers.Run` 契约的前提下完成。

### 4.3 指定日期重跑接口

新增 `phoenix/server/suffer/web-api/pkg/reconciliation/` Handler，并在 `phoenix/server/suffer/web-api/routers/register.go` 注册。提供：

```text
POST /reconciliation/daily-summary/rerun
Content-Type: application/json
{
  "statDate": "2026-08-13"
}
```

- `statDate` 必填，格式固定为 `YYYY-MM-DD`，按上海自然日解释；拒绝空值、非法日期和未来日期。
- Handler 仅绑定参数、调用服务和使用仓库统一 JSON 响应；业务判断、锁定和计算不得放入 Handler。
- 在当前没有异步任务队列/worker 的事实下，接口同步执行并返回本次 `executionLogId`、`statDate`、`trigger`、`status`、`calcVersion`、开始/结束时间。执行失败返回统一错误响应，并返回或可从日志定位 `executionLogId`。
- 接口继续受现有 `webAuth.Middleware()` 保护；动作执行必须按现有权限资源机制为该写操作配置受控权限，不能以匿名公开接口交付。具体资源 ID/角色归属沿用当前权限数据写入方式，若测试环境没有资源初始化数据，应在部署说明中列出。

### 4.4 并发、幂等与执行日志

前置模型不包含本任务所需的执行治理记录；动作执行需在 `phoenix/server/suffer/service/reconciliation/repository/model.go`、Repository、DTO 和前置 DDL 中**增补**以下最小持久化能力，并保证 Entity/DDL 一致：

| 数据 | 最小字段与约束 | 用途 |
| --- | --- | --- |
| `ReconciliationRunState` / `reconciliation_run_state` | `stat_date`（唯一）、`status`、`lease_token`、`lease_expire_at`、`last_execution_log_id`、`last_calc_version`、审计字段 | 对同一统计日期建立数据库级互斥状态，防止 cron 与人工接口或多实例同时写同一日快照。 |
| `ReconciliationExecutionLog` / `reconciliation_execution_log` | `stat_date`、`trigger`、`status`、`calc_version`、`started_at`、`finished_at`、`duration_ms`、`error_code`、`error_message`、`error_detail`、`result_summary`、`created_by` | 每次触发保留一条历史日志，可从日期、状态和日志 ID 检索失败原因；日志不可因重跑覆盖。 |

执行规则如下：

1. 首先创建一条 `RUNNING` 执行日志，并以 `stat_date` 的状态行取得租约；同日已有未过期 `RUNNING` 租约时，新的 cron 或人工请求拒绝执行，返回正在运行的日志 ID，不产生第二套计算。
2. 成功时更新同一执行日志为 `SUCCEEDED`，写入耗时、版本和汇总数量；失败时更新为 `FAILED`，写入稳定错误码、简明 `error_message` 与可定位的 `error_detail`（日期、步骤、缺失配置/主体/来源键等），不得只记录 `error` 字符串。
3. 进程异常留下的过期租约可被后续触发接管；接管前将旧日志标记为 `ABANDONED` 或等价终态并记录接管原因。不得永久阻塞该日期重跑。
4. 重跑不删除人工录入账户状态或人工对账流水；仅覆盖可再生的人工/上游日汇总、系统账户状态和未处理预警计算字段。对状态已被人工标记为已确认、已忽略、已修复的预警，保留处理状态、备注、处理人和处理时间，同时更新本次计算值和 `calc_version`；若重算后差异不再超过阈值，应将其标记为已恢复/不再预警的明确终态，而不是物理删除。

### 4.5 差异预警规则

- 默认阈值为 `0.05`（5%），本次执行将实际阈值写入每条 `AccountStatusDiffAlert.threshold_rate`；阈值配置化属于后续需求，本任务不得在代码中散布多个魔法值。
- 需要比较 `debt_amount_rmb`、`debt_amount_u`、`balance_amount_rmb`、`balance_amount_u` 四个字段。只有同日系统状态和人工状态均存在的主体才可产生可比较预警；缺失人工状态不伪造差异，须在执行结果摘要中报告缺失主体数。
- 差异值为 `manual - system`，差异率沿用本文件第 2 节已确认公式；严格大于 `5%` 才创建/激活预警，等于 `5%` 不预警。
- 预警记录按 `stat_date + subject_id + field_name` upsert；不得因重跑写出重复预警。预警详情必须携带系统值、人工值、差异值、差异率、阈值和计算版本，供后续查询与人工跟进。

## 5. 错误处理与可观测性

1. 将错误分成至少以下可识别类别：`INVALID_STAT_DATE`、`FUTURE_STAT_DATE`、`RUN_ALREADY_ACTIVE`、`MISSING_PRICING_CONFIG`、`MISSING_TIP_RATIO`、`MISSING_EXCHANGE_RATE`、`MISSING_SUBJECT_MAPPING`、`UNCONFIRMED_SOURCE_MAPPING`、`DATABASE_ERROR`、`CALCULATION_ERROR`。名称可按项目常量风格调整，但 API 响应与执行日志必须一致。
2. `log.Printf` 应记录 `executionLogId`、`statDate`、触发来源、步骤、耗时和错误码；禁止输出数据库凭据或人工备注中的敏感内容。
3. 对没有可结算来源、缺失配置或映射的日期，执行结果必须为失败或明确的不可结算状态；不得产生零值成功快照。对于没有人工账户状态的主体，汇总可成功，但必须在 `result_summary` 统计该缺口，且不生成该主体的预警。
4. 手工重跑接口的错误响应必须保留足够定位信息（至少 `executionLogId` 和稳定错误码）；详细堆栈只进入服务日志/执行日志，不直接回传客户端。

## 6. 约束与非目标

- 不实现前端工作台、日汇总查询接口、配置/人工流水/人工账户状态 CRUD；这些由其他任务负责，本任务只提供执行和指定日期重跑入口。
- 不擅自确定订单失败状态、`PAY/GIVEN/CONSUMER/REFUND/BK` 的财务归属、RMB/U 原始币种、系统欠款公式或账户主体映射。未确认时按本文件失败处理。
- 不修改 `account_detail`、`order_record`、dashboard 或 Kakrolot/Barry 的模型和对外接口；不得用 dashboard 的绝对值展示结果直接作为对账总账。
- 不使用内存锁作为唯一并发控制；多实例下必须以数据库持久化状态/租约保证同日串行。
- 不把执行日志当作替代业务审计；业务日表仍须沿用前置模型的自然键、`calc_version` 和 `db.BaseEntity` 审计语义。

## 7. 验收标准

1. `web-api` 启动后只有一个显式配置为 `Asia/Shanghai` 的 00:10 cron 任务；它在 2026 年 8 月 14 日 00:10（上海时间）处理的统计日期必须是 2026 年 8 月 13 日，且服务启动本身不触发补跑。
2. 对指定合法日期调用 `POST /reconciliation/daily-summary/rerun` 能调用与 cron 相同的服务入口；空日期、格式错误日期和未来日期被拒绝，且错误不写入日汇总。
3. 成功执行按前置自然键写入/更新人工日汇总、上游日汇总、系统账户状态和预警；对同一日期连续重跑不新增重复日表或预警记录，并更新 `calc_version` 和执行日志。
4. 同一日期的 cron 与手工重跑、或两个手工重跑并发时，只允许一个执行持有租约；其他调用返回正在执行的日志 ID，不会并发改写快照。
5. 缺失用户价格、小费比例、汇率、账户主体映射、已确认来源映射或发生数据库错误时，业务快照事务回滚，执行日志含日期、步骤、稳定错误码和可定位详情，后续可在修复数据后重跑。
6. 差异预警对四个账户字段使用高精度计算：系统非零采用相对差；系统零/人工非零为 100%；两者为零为 0%；差异率严格超过 5% 才激活预警，并将实际阈值写入记录。
7. 重跑不会删除人工流水或人工账户状态，也不抹除已处理预警的跟进信息；重算后不再超阈值的预警进入明确恢复终态。
8. 为日期解析、自动日期计算、差异率边界、自然键幂等、并发租约、失败日志和重跑 Handler 至少补充单元测试；在各相关 Go module 中执行受影响包的 `go test`，并记录结果。

## 8. 风险与待确认

1. **业务字典阻塞：**订单状态口径、账户流水财务归属与符号、用户分层单价、账户主体映射和系统欠款公式尚未在代码中存在；没有这些确认，任何对应日期都必须失败，不能生产权威汇总。
2. **前置实现状态：**目前仅能在 `doc/` 中看到前置任务的模型约定，未在 `phoenix/server/suffer/service/reconciliation` 发现已落地文件。动作执行前须确认前置任务是否已交付或在本次合并中补齐。
3. **运行拓扑：**现有 `routers.Run` 没有显式优雅关闭钩子；若生产以多副本运行，数据库租约是正确性的必要条件，cron 仍会在每个实例触发但只有一个实例可执行。
4. **同步重跑时长：**当前没有异步 worker，接口采用同步执行。若历史日期数据量使 HTTP 超时，应另行拆分“异步任务队列和日志查询”任务，不能在本任务中临时引入未治理的后台 goroutine。
5. **首次补算：**首次生产补算的起止日期、源库保留期限和受控导入格式未确认；本任务只提供单日执行机制，不授权批量历史补算。

## 9. 后续任务建议

1. 在业务方确认后，将订单状态、流水类型、金额符号、主体映射和欠款公式固化为可版本化配置，并用已对账样本做月度试算。
2. 另行提供日汇总、执行日志和预警的查询接口及前端跟进页，避免运维只能查数据库定位失败。
3. 当同步重跑无法满足生产时，新增独立 worker/队列、重试策略、运行指标和告警，而不是改变本任务接口的同步语义。
