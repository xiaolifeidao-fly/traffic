# 明确对账数据来源、口径与迁移边界

## 1. 任务目标

本任务仅完成「梳理需求」：将 `phoenix/demo/reconciliation-requirements.md` 中资金出入账对账工作台的原型口径，映射到 Phoenix 当前实际存在的订单、账户、流水和看板实现，并明确可复用数据、必须新增的数据能力、历史补算范围及异常处理边界。**本阶段不修改任何业务代码或表结构。**

结论：Phoenix 已有 `order_record`、`account`、`account_detail` 及基于它们的 dashboard 聚合；但原型要求的 `order_sum_record`、双币种金额、用户分层/单价、人工出入账流水、账户主体、每日账户状态、汇率/小费/代付配置、预警记录和定时调度均不存在，不能把原型表名或字段当成现有来源直接使用。

## 2. 当前工程事实

| 项目 | 结论 | 依据 |

| 现有接口边界 | 已注册 `/account/*`、`/order/*` 和当天 dashboard 接口；没有 `/reconciliation/*` 接口或 reconciliation 服务域。 | `phoenix/server/suffer/web-api/routers/register.go`；`phoenix/server/suffer/web-api/pkg/account/account.go`；`phoenix/server/suffer/web-api/pkg/dashboard/dashboard.go` |
| 表创建与删除约定 | 现有服务通过 `EnsureTable()`/`AutoMigrate()` 建表；实体使用 `db.BaseEntity`，其中包含 `active` 逻辑删除和 `created_time`/`updated_time`。新对账实体应沿用这一约定，不按原型另造 `deleted_at` 语义。 | `phoenix/server/suffer/service/account/repository/repository.go`；`phoenix/server/common/middleware/db/base.go` |

## 3. 数据来源与字段映射

### 3.1 人工维度（只读日汇总）

| 原型字段/口径 | 可用现有字段 | 落地映射及边界 |
| --- | --- | --- |
| 任务数量（大户/小户/其他） | `order_record.user_id`、`order_status`、`order_num`、`init_num`、`end_num`、`created_time` | 可按用户和统计日取订单，但**不能**直接复用原型的 `order_sum_record`。当前仅有 dashboard 的完成量公式；“待审核/失败/审核成功”的状态映射必须由业务确认后单独实现。 |
| 大户/小户/其他 | 无 | 新增版本化用户分层与单价配置；默认其他用户。历史统计按 `stat_date` 命中的配置版本计算。 |
| 应出款金额 | `order_record` 的 `price`、`order_amount` 可供核验 | 原型要求“单价 × 任务数”，不能直接以 `order_amount` 替代，除非业务确认它与结算单价含义一致。汇总应保存当日生效单价和计算出的应出款金额。 |
| 代付金额/实际出款/人工总出款 | 无 | 新增全局代付比例配置及日汇总字段；仅 RMB 计算：`代付金额 RMB = 应出款金额 RMB × payout_ratio`，`人工总出款 RMB = 应出款金额 RMB - 代付金额 RMB`。U 的代付值默认 `0`，除非后续确认另有 U 代付规则。 |
| 当前余额 | `account.balance_amount` | 仅有无币种的账户余额，且账户与大/小/其他用户分层、统计日余额之间无现成映射；不得直接填入分层余额。需通过账户主体/用户映射及余额时点规则新增计算。 |

**统计日期规则：**以 `Asia/Shanghai` 自然日为准，查询窗口统一为 `[stat_date 00:00:00, stat_date + 1 日 00:00:00)`；现有表只保存 `created_time`，其数据库时区和业务发生时点是否一致尚未在代码中声明，首次上线前必须核验生产库时区与历史数据写入方式。

### 3.2 上游维度（只读日汇总）

| 原型字段/口径 | 可用现有字段 | 落地映射及边界 |
| --- | --- | --- |
| 充值金额 | `account_detail.type='PAY'`、`amount` | 当前 dashboard 把 `PAY` 与 `GIVEN` 相加称为充值。对账日汇总应拆分保存；建议在业务确认后将 `PAY` 映射为充值金额。 |
| 返点金额 | `account_detail.type='GIVEN'`、`amount` | `GIVEN` 在 dashboard DTO 中展示为 `givenAmount`，可作为“返点”的**候选来源**；原型未给出枚举对应关系，必须由财务确认后固定。 |
| 消费金额 | `account_detail.type='CONSUMER'`、`amount` | 可作为候选来源；`REFUND`、`BK` 在现有 dashboard 是对消费的扣减项，原型是否将它们纳入消费净额需业务确认。不能无声丢弃。 |
| 小费金额 | 无 | 新增按日期生效的 `tip_ratio` 配置与汇总留痕；`小费 = 消费金额 × tip_ratio`。 |
| 应收金额 | 充值、返点汇总值 | 业务确认后按 `应收 = 充值 - 返点` 计算；不以 dashboard 的“PAY + GIVEN”总额替代。 |
| 真人/其他社区 | `account.id -> account.user_id`，可连接用户信息 | 当前没有上游类型、社区或主体映射字段，不能从 `account_detail` 自动区分。新增账户主体配置/映射并支持有效期。 |

### 3.3 出入账（人工维护明细和区间汇总）

原型要求的 `record_date`、入账/出款类型、固定类目、RMB/U 金额、RMB/U 手续费、备注与操作人，在 `account_detail` 中均没有完整对应字段。`account_detail` 也允许修改与逻辑删除，无法满足对账总账的可追溯性要求。

因此新增独立的对账流水表（建议 `reconciliation_ledger_record`），不复用或改写 `account_detail`：

- 关键字段：`record_date`、`record_type`（`INCOME`/`PAYOUT`）、`category`、`amount_rmb`、`amount_u`、`fee_rmb`、`fee_u`、`remark`、创建/更新人、`active`。
- 固定类目：入账为“社区入账、其他入账”；出款为“大户出款、小户出款、其他用户出款、服务器出款、其他出款”。服务层校验类型与类目的组合。
- 汇总按日期区间、类型、类目聚合四个金额字段，并给出总入账、总出款、净入账；明细只允许通过该表的 CRUD 接口修改。
- 金额使用 decimal 字符串/高精度 decimal，不使用 `float64` 作为入库或计算精度；与现有金额字段 `decimal(38,8)` 风格一致。

### 3.4 账户状态与预警

| 原型字段 | 当前可用来源 | 缺口及实施要求 |
| --- | --- | --- |
| 系统账户余额 | `account.balance_amount` | 无币种和账户主体；仅能作为已映射账户的候选余额来源。需明确每个主体对应的 Phoenix 账户、外部来源或计算规则。 |
| 系统欠款 | 无 | 当前订单、账户与 dashboard 均没有欠款字段或计算方法；必须为 AK、社区、代收方逐一配置公式/外部来源，不能由余额反推。 |
| 人工录入余额/欠款 | 无 | 新增按日期、主体、双币种的人工日明细。社区新建应先创建/启用主体配置，再引用主体 ID。 |
| 差异预警 | 无 | 新增预警记录。按 `stat_date + subject_id + field_name` 比较系统与人工同日记录：系统值不为 0 时 `abs(manual-system)/abs(system)`；系统值为 0 且人工非 0 时为 `100%`；两者均为 0 时为 `0%`。默认阈值 `5%`，阈值本身需配置并在预警中留痕。 |

账户状态采用独立的 `account_subject_config`、`account_status_system_daily`、`account_status_manual_daily` 与 `account_status_diff_alert`。系统表是每日计算结果明细，人工表是人工日录入明细；两者都不是可由当前 `account` 表替代的快照。

### 3.5 RMB/U、手续费及审计口径

- Phoenix 当前订单、账户和流水模型均只有一个无币种数值字段；仓库内未发现汇率、币种、RMB/U、手续费或小费字段。对账服务必须将 RMB/U 分别落列，禁止根据现有单金额字段猜测币种。
- 对原始来源只有 RMB 的指标，使用统计日有效汇率计算 `amount_u = amount_rmb × exchange_rate`；`exchange_rate` 的单位固定为“1 RMB 可兑换多少 U”。原始即有 U 的数据优先保存原值，并记录 `currency_source=RAW_U`；由 RMB 换算的记录标记为 `CONVERTED_FROM_RMB`。
- 新增 `exchange_rate_snapshot`，以 `rate_date + RMB + U` 唯一；人工/上游日汇总保存 `exchange_rate_snapshot_id` 或已用 `exchange_rate`，使历史重跑和审计可复现。
- 原型中的手续费只属于人工对账流水，不能从 `account_detail.amount` 推导；手续费不混入金额字段，单独按币种汇总。

## 4. 需交付的后续实现内容

建议在 Phoenix 新增 `service/reconciliation` 与 `web-api/pkg/reconciliation`，按当前仓库的 Entity → Repository → Service → Handler 分层实现，并在 `web-api/routers/register.go` 注册。实施时新增或补齐以下能力：

1. **配置和映射：**用户分层单价（含生效区间）、代付比例、小费比例、汇率快照、账户主体和主体到账户/外部数据源映射。
2. **明细与日汇总：**独立对账出入账流水、人工维度日汇总、上游维度日汇总、系统账户状态日明细、人工账户状态日明细和预警记录；所有日表以统计日期与业务维度建立唯一键并支持幂等重算。
3. **查询和维护接口：**实现原型建议的 `/reconciliation/overview`、ledger、account-status 和 config 接口；不改变既有 `/account/*`、`/dashboard/*` 对外契约。
4. **日任务与重跑：**补充明确的调度承载方式及执行日志。每日 `00:10 Asia/Shanghai` 处理前一自然日；重跑按指定日期覆盖同一唯一键的汇总/系统结果，并重新生成同日预警。
5. **审计与异常：**金额计算和保存采用 decimal；失败批次、缺失配置、无汇率、无法映射上游主体、源数据冲突均记录执行日志并标记失败，不产出部分“成功”汇总。

## 5. 首次补算与迁移边界

### 5.1 首次补算范围

- **不自动全量补算。**当前代码未包含可证明的历史开始日期、`order_sum_record` 或可回溯的 RMB/U/手续费数据；首次范围必须由业务在上线前指定 `backfill_start_date` 和 `backfill_end_date`，并完成源表可用性核验。
- 建议先选定一个已对过账的完整自然月做试补算，与人工台账逐日核对后，再按确认范围分批补算；未能映射的日期不得默认为 0 后标记成功。
- 订单可从 `order_record.created_time` 回放候选任务量，但缺少原型“失败”定义和历史用户分层/单价；未覆盖配置生效期的日期不能生成权威人工维度。
- 上游维度可从 `account_detail.created_time` 回放 `PAY`、`GIVEN`、`CONSUMER` 等候选流水，但缺少历史币种、上游分类、小费和汇率；这些历史字段必须先补配置/补录，或将该日期标记为不可结算。
- 原型人工出入账、手续费、人工账户状态均无现存完整来源；首次数据须通过受控导入写入新表并保留导入批次、来源文件标识和操作人，不能从现有 `account_detail` 猜测迁移。

### 5.2 不迁移与兼容边界

- 不修改或重解释 `account_detail` 的历史 `type`、金额符号、`description` 和 `business_id`；它保留为 Phoenix 既有账户流水来源。
- 不以 dashboard 的当天接口替代对账查询。dashboard 使用当天窗口、绝对值展示及专有退款/BK扣减规则，对账须按明确日期区间、原始金额和确认后的枚举规则计算。
- 不依赖 `order_record_snapshot_daily` 作为对账来源；当前仅有读取查询和索引 SQL，未发现实体/写入逻辑，数据完整性未证实。
- 不迁移或改变 Kakrolot/Barry 现有上游契约。本功能作为 Phoenix 的新上游对账能力，读取本地已同步数据；如确需外部账户/社区数据，应通过独立适配和幂等导入，不修改既有调用方契约。

## 6. 约束与非目标

- 本任务不实现对账服务、表、接口、定时任务或前端页面；后续动作执行必须以本文件为准。
- 人工维度和上游维度在页面保持只读；只有独立对账流水、人工账户状态、配置和预警处理允许写操作。
- 不把原型中建议表名视为已存在物理表；正式实体名称和索引可在开发任务中按 Phoenix 命名与迁移约定定稿。
- 不使用 `float64` 保存/累计对账金额；展示层可以转换，账务计算必须保持 decimal 精度。
- 遇到同一来源记录重复、业务主键冲突、负数方向不符合确认规则、缺失汇率/配置/主体映射或统计窗口跨时区不确定时，任务应失败并留下可追踪异常，而非静默归零。

## 7. 验收标准

1. 开发前能依据本文件定位每一项原型字段到现有真实字段，或明确标记为新增/待确认；不得引用不存在的 `order_sum_record` 作为 Phoenix 已有表。
2. 订单、上游流水、出入账、账户状态四类数据均给出来源、统计日期、币种、精度、可编辑性和缺口边界。
3. 对 `PAY`、`GIVEN`、`CONSUMER`、`REFUND`、`BK` 的对账归属在上线前完成财务确认，并以枚举/配置固化；未确认类型不进入日汇总。
4. RMB/U 同时支持原始值与按日汇率换算值，历史汇总可通过保存的汇率/快照复算；手续费独立于金额。
5. 所有日汇总和系统账户状态按上海自然日、唯一键和幂等重跑规则执行；重跑不会产生重复数据，且会重算预警。
6. 人工账户状态与系统账户状态按日期、主体、字段比较，正确处理系统值为 0 的差异率，并在超过默认 5% 阈值时生成可处理预警。
7. 首次补算必须有明确的起止日期、配置覆盖核验和异常清单；缺少不可回溯字段的数据不能被标为已对账。

## 8. 风险与待确认

1. **订单状态口径：**原型的待审核、失败、审核成功与 Phoenix `INIT/PENDING/DONE/REFUND/REFUND_PENDING` 的对应关系尚未确认，尤其“失败数量”无现成状态。
2. **金额语义与符号：**`account_detail.amount` 的正负方向、`PAY/GIVEN/CONSUMER/REFUND/BK` 与充值、返点、消费的财务对应关系需财务签字确认；不得仅依据 dashboard 的绝对值展示推断。
3. **双币种来源：**现有表未记录币种。需确认 U 的真实业务含义、历史是否有原始 U、汇率数据源及“1 RMB = x U”的有效期和精度。
4. **上游/账户主体：**真人、其他社区、AK、社区、代收方与 Phoenix `account`/`user` 或外部系统的映射规则未知；系统欠款的计算公式也未提供。
5. **历史数据完整性：**`order_record_snapshot_daily` 没有找到写入实现；不能证明可用。首次补算日期、源库保留期限和人工台账导入格式需在开发前确认。
6. **调度承载：**当前 Suffer 服务内未找到调度框架；需决定由应用内调度、独立任务进程还是平台调度触发，并定义幂等锁、执行日志、失败重试和人工重跑权限。

## 9. 后续任务建议

1. 先完成“确认订单状态、流水类型、金额符号和主体映射”的业务数据字典及样本对账任务。
2. 再完成 reconciliation 配置、实体/Repository、流水与账户状态接口的后端开发任务。
3. 最后完成日汇总/重跑任务、首次补算导入和对账验收报告；生产补算前应以已对账月份进行试运行。
