# 实现对账工作台查询、录入与配置 API

## 1. 任务目标

为 Phoenix 新管理端的资金对账工作台增加受鉴权保护的 `/reconciliation` HTTP API：读取已生成的人工/上游日汇总和系统账户状态，维护人工出入账、人工账户状态及对账配置，并查询、处置差异预警。本阶段只完成需求梳理，不改业务代码。

本任务依赖：

- `reconciliation-backend-0d79cc3a4e`：定义 `reconciliation_` 数据模型、DTO 与 Repository。
- `reconciliation-backend-dcbf2ae425`：定义按上海自然日生成日汇总、系统账户状态、预警及手工重跑的计算职责。

动作执行前必须确认上述两个任务的代码已合入当前分支；当前工作区尚不存在 `phoenix/server/suffer/service/reconciliation` 或 `phoenix/server/suffer/web-api/pkg/reconciliation`。

### 3.2 工作台读取接口

所有日期使用 `YYYY-MM-DD`，按 `Asia/Shanghai` 自然日解释；`startDate`、`endDate` 均必填，且 `startDate <= endDate`。列表接口应复用 `baseDTO.PageDTO`（`total` + `data`），空结果返回空数组而不是 `null`。

| 路由 | 用途与请求 | 返回和规则 |
| --- | --- | --- |
| `GET /reconciliation/overview` | `startDate`、`endDate`。 | 返回同一区间的人工汇总、上游汇总，以及由已保存快照计算出的人工实际出款/上游应收总计；不得临时读取当前配置重算历史。 |
| `GET /reconciliation/manual-daily-summaries` | 日期区间、可选 `userLevel`、分页。 | 只读 `ManualDailySummary`；返回当日单价、代付比例、汇率、`calcVersion` 等快照字段。 |
| `GET /reconciliation/upstream-daily-summaries` | 日期区间、可选 `upstreamType`、分页。 | 只读 `UpstreamDailySummary`；返回小费比例、汇率及应收快照。 |
| `GET /reconciliation/ledger-records` | 日期区间、可选 `recordType`、`category`、`subjectId`、`importBatch`、分页。 | 返回有效人工流水及主体展示字段；支持页面按类目汇总时，应由 Service 从同一过滤集计算并在响应中提供 `income/payout` 的 RMB/U/手续费汇总，不能由前端再以浮点数累计。 |
| `GET /reconciliation/system-account-statuses` | 日期区间、可选 `subjectId`、`subjectType`、分页。 | 只读 `SystemAccountStatusDaily`，返回主体快照与四个金额字段；不允许修改/删除。 |
| `GET /reconciliation/manual-account-statuses` | 日期区间、可选 `subjectId`、`subjectType`、分页。 | 返回人工录入状态及备注；同日期同主体最多一条。 |
| `GET /reconciliation/alerts` | 日期区间、可选 `subjectId`、`status`、`fieldName`、分页。 | 返回预警的系统值、人工值、差额、差异率、阈值和处置审计字段；查询不触发重新计算。 |

### 3.3 录入、配置与预警处置接口

| 路由 | 行为与约束 |
| --- | --- |
| `POST /reconciliation/ledger-records` | 新建人工流水。请求仅接受 `recordDate`、`recordType`（`INCOME`/`PAYOUT`）、`category`、`subjectId`、金额/手续费（RMB/U 字符串）和 `remark`；普通人工入口不得接收或伪造 `sourceType`、`sourceReference`、`importBatch`。主体必须存在且启用。 |
| `PUT /reconciliation/ledger-records/:id` | 更新有效人工流水；修改后的金额、日期、类型、类目和主体重新校验。不得以更新接口把人工流水转换为外部/导入流水。 |
| `DELETE /reconciliation/ledger-records/:id` | 仅设置 `active=0`，不物理删除；已失效流水从默认查询和后续重算来源中排除。若业务确认“流水修改后自动重算”前尚未落定，本任务只保存变更，不在 HTTP 请求内隐式执行重算。 |
| `POST /reconciliation/manual-account-statuses` | 创建人工账户日状态；以 `(recordDate, subjectId)` 唯一。重复自然键返回明确冲突错误，不能默默新增第二条。写入时从启用主体复制 code/name/type 快照。 |
| `PUT /reconciliation/manual-account-statuses/:id` | 更新既有人工账户日状态；不得改变其自然键，也不得改写主体快照为任意客户端值。 |
| `PUT /reconciliation/alerts/:id/handling` | 仅允许处置字段：`status`、`followRemark`；`handledBy` 从认证上下文 `auth.user` 写入，`handledAt` 由服务端生成。严禁客户端修改系统值、人工值、差额、差异率或阈值。状态枚举和“重算后已处理预警如何恢复/关闭”规则沿用前置计算任务的最终实现。 |
| `GET/POST/PUT/DELETE /reconciliation/user-pricing-configs[/ :id]` | 维护用户分层/单价的版本化配置。创建和更新校验 `scopeType`（`USER`/`LEVEL_DEFAULT`）、`userId` 与 `userLevel` 的组合、非负 decimal 单价/比例、生效日与唯一自然键；默认分层配置使用 `userId=0`，不得以缺失配置补零。删除采用逻辑删除。 |
| `GET/POST/PUT/DELETE /reconciliation/tip-ratio-configs[/ :id]` | 维护按 `effectiveDate` 生效的小费比例；同日唯一，比例必须为非负 decimal，删除采用逻辑删除。 |
| `GET/POST/PUT/DELETE /reconciliation/exchange-rates[/ :id]` | 维护按 `rateDate + currencyFrom + currencyTo` 唯一的汇率；币种必须非空、汇率必须大于零，保留 `source` 与 `remark`。删除采用逻辑删除。 |
| `GET/POST/PUT/DELETE /reconciliation/account-subjects[/ :id]` | 维护 AK、社区、代收方等账户主体；`subjectCode` 全局唯一，新增/编辑须校验名称、类型、状态、排序。已经被历史状态/流水快照引用的主体停用而非物理删除；普通写入拒绝使用停用主体。 |

`[/ :id]` 在动作执行时应落实为无空格的 Gin 模板：列表/创建为同一路径，更新/删除为 `/:id`。鉴于当前权限表不区分 HTTP method，读写共用模板会共用一项资源授权；本任务的初始 SQL 统一仅授予管理员。若产品要求“可读不可写”的角色，须另行改造权限模型或把写操作拆为不同路由模板，不能误以为同 URL 的 GET/POST 能分开授权。

## 4. 设计要求

### 4.1 服务、输入与输出

1. 所有 Handler 使用 `ShouldBindQuery` / `ShouldBindJSON`，绑定或路径 ID 失败时使用 `routers.ToError`；Service 返回可识别业务错误，Handler 不泄露 GORM 错误细节。
2. 金额、比例和汇率的 JSON/Query DTO 均为 decimal 字符串；Service 使用高精度 decimal 运算和格式校验，不接受 NaN、科学计数法、空字符串或 `float64` 近似值。
3. `pageIndex`、`pageSize` 使用仓库既有分页 DTO；Service 负责默认值和最大页大小。日期范围必须限制在允许的业务窗口，具体最大跨度若产品未确认先在 DTO/Service 常量中集中定义并记录为待确认，不在 Handler 中散落魔数。
4. 写接口从 Auth context 取登录用户写入 `created_by` / `updated_by`；不得信任请求体中的操作人、处理人或主体快照字段。
5. 修改、删除不存在或已逻辑删除的记录返回明确的“not found”；唯一键冲突、停用主体、非法日期、无效 decimal、零/负汇率分别返回可区分业务错误。

### 4.2 快照、状态与一致性

1. 工作台读取人工/上游汇总及系统状态时，只读取前置计算任务落库的快照；不得在查询请求内重新扫订单、`account_detail` 或当前配置进行计算。
2. 流水、人工账户状态和配置的多字段变更在同一数据库事务完成；更新自然键相关字段时先做唯一性校验，数据库唯一键仍是最终兜底。
3. 系统账户状态、日汇总和预警不是本任务的常规 CRUD 对象；本任务只暴露查询与预警处置，不新增删除/手改快照接口，也不重复实现 `POST /reconciliation/daily-summary/rerun`。
4. 预警“处理”只能写治理字段。后续重算如何保留、关闭或恢复已处理预警，必须复用前置任务实现的状态机，不能由本任务的 Handler 覆盖计算字段。
5. 配置与主体默认查询排除 `active=0`；历史汇总、系统状态和预警始终使用已保存的当日快照，不因配置/主体后续修改改变历史展示。

### 4.3 路由和权限资源

1. `ReconciliationHandler` 注册的所有路由均使用普通 `engine.GET/POST/PUT/DELETE`，不得调用 `auth.Public*`；由全局 `auth.Middleware()` 统一鉴权。
2. `add_reconciliation_resources.sql` 对每个实际 Gin 模板写入同名 `resource_url`，包含 `:id` 和 `/handling` 模板；SQL 必须按 URL 判重，并幂等绑定管理员角色。
3. 新增资源的 `code` 必须唯一且表达领域/动作；菜单资源不在本任务创建，除非管理端路由与菜单信息已另行确认。
4. 权限测试至少验证：无 token 被拒绝、资源未配置被拒绝、管理员角色拥有 SQL 中的资源后可访问；对带 `:id` 的路由验证 Auth 实际查找的是模板 URL。

## 5. 约束与非目标

- 本轮只更新需求文档；动作执行才可修改 Go、SQL 和测试文件。
- 不创建前端页面，不修改 Kakrolot 或 Barry 既有接口契约；这是 Phoenix Suffer 的新上游管理 API。
- 不在本任务引入异步队列、导入文件协议、批量补算或新的定时任务；受控导入与日汇总重跑分别由后续/前置任务负责。
- 不重用 `account_detail` 作为可编辑对账流水表，也不以 dashboard 的展示型统计替代对账快照。
- 不物理删除人工流水、配置或账户主体；不开放系统汇总、系统账户状态和预警计算字段的直接编辑。

## 6. 验收标准

1. `web-api` 能构造并注册唯一的 reconciliation Handler，`registerHandler()` 包含该 Handler，所有 `/reconciliation` 路由均经过既有 Auth middleware 和统一 JSON 响应。
2. 概览、人工/上游日汇总、流水、系统/人工账户状态和预警接口均按合法日期区间和分页查询；空数据返回结构稳定，日期非法、倒置区间和非法分页参数被拒绝。
3. 日汇总和系统账户状态 API 只读已落库快照，响应包含计算版本及当日配置/主体快照，不在查询路径触发重新计算。
4. 人工流水可创建、更新、逻辑删除并按日期、类型、类目、主体、导入批次分页过滤；普通人工请求无法写入外部来源幂等字段，金额与手续费保持 `DECIMAL(38,8)` 精度。
5. 人工账户状态按 `(recordDate, subjectId)` 唯一创建和更新，主体快照由服务端取得；系统账户状态没有写接口。
6. 用户分层单价、小费比例、汇率和账户主体均有分页查询与受校验的 CRUD；生效日/币种对/主体编码等自然键冲突、停用主体、零或负汇率和无效 decimal 都返回明确错误。
7. 预警可按日期、主体、状态、字段查询，处置接口只能修改状态、跟进备注及服务端审计字段，不能改写差异计算结果。
8. `add_reconciliation_resources.sql` 覆盖每个实际路由模板，幂等授予管理员；测试证明资源 URL 与 `:id` 模板匹配，未授权请求被拒绝。
9. 对新增或受影响的 `service/reconciliation`、`web-api/pkg/reconciliation` 和路由/鉴权包执行相应 `go test`；在 `web-api` 和 `service` 各自 Go module 中记录命令和结果。

## 7. 风险与待确认

1. **前置代码交付：**当前仅存在前置任务文档，工作区没有 reconciliation 包。若前置模型或日汇总实现尚未合入，本任务无法编译，动作执行须先合并或以明确依赖顺序实现。
2. **权限粒度：**现有 `resource_new` 按 URL 而非 HTTP method 授权。同一路径的列表/创建或读取/更新不能分权；若运营角色需要只读权限，需产品确认采用动作型子路径还是独立权限模型改造。
3. **预警状态机：**已处理/已忽略预警在重算后差异仍存在、差异消失时的状态转移尚待业务确认；本任务只能限制手工处置字段，不能臆定重算覆盖规则。
4. **流水变更后的重算时机：**人工流水和人工账户状态保存后是立即触发、提示用户手动重跑还是下一日任务重算，尚未确认；为避免 HTTP 写请求隐式产生长事务，本任务默认不触发重算。
5. **日期窗口与枚举字典：**查询最大时间跨度、账户主体类型、流水类目及预警处置状态的最终枚举尚未在代码中固化；必须在实现前由产品/财务确认，不能用前端显示文本代替后端受控枚举。

## 8. 后续任务建议

1. 当前置代码可用后，按本接口文档先实现 Repository/Service 单元测试，再接 Handler、路由与权限 SQL，避免在 Handler 层补业务规则。
2. 财务确认流水变更重算策略和预警状态机后，为写操作补受控的单日重算入口/提示与操作审计，而不是在每次编辑中隐式执行全量计算。
3. 如需为非管理员提供只读工作台，单独评审 URL 级权限模型的读写分离方案及迁移策略。
