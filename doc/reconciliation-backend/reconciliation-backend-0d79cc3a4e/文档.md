# 建立对账配置、流水与日汇总数据模型

## 1. 任务目标

本任务仅完成「梳理需求」：为 Phoenix 新增一个独立的 `reconciliation` 服务域数据基础，定义可追溯、可按日期幂等重跑的配置、人工出入账流水、人工/上游日汇总、账户状态与差异预警模型，以及与现有 Go 分层一致的 DTO、Repository 和 MySQL 迁移边界。**本阶段不修改业务代码、表结构、路由、定时任务或前端。**

完成后，后续动作执行可按本文件新增实体与仓储；汇总、系统状态和预警的生产者由后续任务实现，但其数据唯一键与审计字段在本任务中先固定，避免后续重跑产生重复账或不可追溯快照。

### 3.3 DTO 与 Repository 约定

1. 每个 Entity 都有只读 `XxxDTO`，嵌入 `baseDTO.BaseDTO` 并暴露实体审计信息；金额、汇率和比例字段保持字符串，日期用项目既有 DTO 习惯表示，不在 DTO 层转浮点。
2. 配置 DTO 包含 `CreateUserPricingConfigDTO`、`UpdateUserPricingConfigDTO`、`CreateTipRatioConfigDTO`、`UpdateTipRatioConfigDTO`、`CreateExchangeRateDTO`、`UpdateExchangeRateDTO`、`CreateAccountSubjectDTO`、`UpdateAccountSubjectDTO`，并提供按状态、主体、日期范围的 Query DTO。
3. 流水 DTO 包含创建、更新、分页查询和按日期区间/类型/类目/主体过滤；`source_type`、`source_reference`、`import_batch` 只允许受控导入路径赋值，普通人工录入不得伪造外部来源幂等键。
4. 人工账户状态 DTO 支持按 `record_date + subject_id` 创建或更新；预警 DTO 仅允许变更 `status`、`follow_remark`、`handled_by`、`handled_at`，禁止前端改写系统值、人工值或差异计算值。
5. Repository 至少提供：按配置生效日查询、按来源引用查询流水、按汇总/状态/预警自然键查询，以及事务内的 upsert 辅助方法。GORM 的 `Save` 不能替代自然键幂等：后续汇总任务必须先按唯一键查找并更新，或使用与 MySQL 唯一键一致的 `ON DUPLICATE KEY UPDATE`。
6. 各 Repository 可以提供 `EnsureTable()` 以匹配当前 `account` 域惯例，但生产部署以 `add_reconciliation_data_models.sql` 为准；两者的表名、列、精度、审计字段、唯一键与索引必须一致，避免 AutoMigrate 漂移。

## 4. 设计要求

### 4.1 统计日期、版本与幂等

- `stat_date`、`record_date`、`effective_date`、`rate_date` 都使用 MySQL `DATE`，语义为 `Asia/Shanghai` 自然日；不能以 UTC 时间戳截断替代。
- 汇总和系统状态使用固定自然键重跑：人工汇总为“日期 + 用户分层”，上游汇总为“日期 + 上游类型”，系统/人工账户状态为“日期 + 主体”，预警为“日期 + 主体 + 字段”。
- 汇总、系统状态、预警必须写入 `calc_version`；后续任务每次重算更新该值和 `updated_time`，并在服务日志/任务日志记录执行批次。`calc_version` 的具体格式（例如代码版本或批次号）由定时任务任务定稿，但不能为空字符串。
- 汇总行中保留实际使用的单价、出款比例、小费比例、汇率；不得在查询时重新关联当前配置推导历史金额。

### 4.2 账务与审计

- 所有业务表均保留 `active`、`created_by`、`updated_by`、`created_time`、`updated_time`。DDL 的审计列类型沿用当前 SQL 的 `VARCHAR(64)` 和 `DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP` 风格；Go Entity 通过 `db.BaseEntity` 复用字段语义。
- `LedgerRecord` 的删除遵循 `active=0` 逻辑删除；删除后的流水不得参与后续汇总。汇总/系统状态/预警是可再生快照，不开放常规删除。
- `amount_*` 与 `fee_*` 分列保存，手续费不得混入金额；正负方向由 `record_type` 与后续财务枚举确定，不能仅根据金额正负推断。
- `source_reference` 为可空字段；由于 MySQL 唯一键允许多个 `NULL`，人工录入不会互相冲突。对非空来源引用，写入前必须同时给出非空 `source_type`，否则服务层拒绝请求。
- 不建立跨现有 `account`、`order_record`、`account_detail` 的物理外键：这些现有表未使用此类约束，且对账需保存主体/配置快照。服务层在写入时验证逻辑关联存在性。

### 4.3 范围内的错误处理

- 生效日配置不存在、同日存在多个启用配置、汇率为零/负数、主体停用但被新写入、来源幂等键冲突、日期不合法、金额/比例非 decimal 格式时，Service 层须返回可识别错误，不能以 `0` 自动补齐。
- 对 `account_detail` 的类型、金额正负及真人/其他社区映射尚未财务确认；本任务只为其结果建模，后续汇总不得先假定 `PAY/GIVEN/CONSUMER/REFUND/BK` 的归属。
- `active=0` 的配置、主体和流水在默认查询中排除；历史汇总保留其当时快照，不因主数据后续停用而改写。

## 5. 约束与非目标

- 本任务不实现 `daily_reconciliation_summary_job`、历史补算、数据导入、差异计算公式、接口、权限资源或前端工作台。
- 不改动 `account`、`account_detail`、`order_record`、dashboard 及 Kakrolot/Barry 的表、接口或既有统计口径；Phoenix 对账以新表承接结果和人工台账。
- 不将 `phoenix/demo/reconciliation-requirements.md` 中的建议表名直接当作现有表；本文件定义的 `reconciliation_` 前缀是本次新域的落地命名。
- 不使用 `float64`，不将历史缺失的币种、汇率、用户层级或账户主体映射伪造成可结算的零值。
- 本任务不新增数据库外键、触发器或自动 SQL 迁移框架；部署方须显式执行迁移 SQL，并在发布前验证库中无同名遗留表/冲突索引。

## 6. 验收标准

1. 新增 `reconciliation` 域的 `repository/model.go`、`repository/repository.go` 和 `dto/dto.go`，文件布局与 `account`、`dashboard` 域一致，且不新增未要求的 Handler/路由。
2. 10 个表均有与本文件一致的 Entity、`TableName()`、`db.BaseEntity` 审计字段、`DECIMAL(38,8)` 金额/比例/汇率字段，以及可定位的 DTO。
3. `add_reconciliation_data_models.sql` 可在 MySQL 重复执行而不因建表或索引失败；DDL 与 GORM 模型的表名、列名、精度、审计列、唯一键和普通索引一致。
4. 配置表能按上海自然日唯一定位生效版本；用户价配置能表达指定用户和按分层的默认回退，汇率能表达任意币种对，且不存在“缺失即零”的默认数据。
5. 导入/外部同步流水以非空 `(source_type, source_reference)` 去重，手工流水按主键编辑/逻辑删除；流水查询拥有日期+类型、主体+日期和导入批次索引。
6. 人工汇总、上游汇总、系统账户状态、人工账户状态和预警分别按本文件规定的自然键唯一；重复执行同一日期计算不会新增重复行。
7. 汇总与系统状态保存当日生效的单价、比例、汇率和主体快照；预警保存系统值、人工值、差额、差异率、阈值和处理审计字段，允许后续追溯计算依据。
8. Repository 对未初始化数据库返回明确错误；自然键冲突、日期/金额格式异常和来源引用冲突由后续 Service 层得到明确可处理错误，而不是静默覆盖或写入零值。

## 7. 风险与待确认

1. **用户价生效规则：**需产品/财务确认 `USER` 覆盖 `LEVEL_DEFAULT` 的优先级、一个用户在同日是否允许变更层级，以及其他用户是否一定使用 `user_id=0` 的分层默认价格。
2. **主体与上游分类：**需确认 `subject_type`、`upstream_type` 的正式枚举、AK/社区/代收方的 `subject_code` 来源，以及现有 `account_detail` 如何可靠映射真人和其他社区。
3. **账务枚举与方向：**需财务确认入账/出款类目、金额正负方向、`PAY/GIVEN/CONSUMER/REFUND/BK` 的归属，以及流水修改/删除后是否必须自动触发相关日重算。
4. **汇率语义：**需确认 U 的币种代码、`exchange_rate` 是“1 RMB = x U”还是其倒数、精度及汇率来源；在确认前不能生成权威双币种汇总。
5. **预警重跑与人工处理：**需确认重算同一自然键时，已确认/已忽略预警是保留人工处理状态并刷新计算值，还是在差异消失后自动关闭；该规则影响 Repository 的 upsert 字段集。
6. **迁移发布：**当前仓库未发现 `web-api/sql` 自动执行器。动作执行前须确认实际部署脚本如何执行 `add_reconciliation_data_models.sql`，并避免只依赖开发环境的 `AutoMigrate()`。

## 8. 后续任务建议

1. 在本数据模型落地后，单独实现配置、流水和人工账户状态的 Service/Handler、权限资源与操作审计。
2. 待财务确认订单状态、流水枚举、主体映射和汇率语义后，实现上海时区日汇总、系统状态、预警重算与任务执行日志。
3. 确认补算日期范围和历史配置覆盖后，再实现受控导入、异常清单与按日期重跑；不得将不可回溯日期标记为已对账。
