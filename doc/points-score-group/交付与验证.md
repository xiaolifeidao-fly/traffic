# 人工商品：价格策略组（领任务积分按权重随机）

2026-10-29 实现。代码在 Barry 与 Phoenix 工作区，未提交、未发布。

需求：商品除了原价，还可以再加几个价格档位；用策略组决定每一单的积分在哪几个档位里、按什么权重随机。用户级别只绑定一个策略组，全局改了组，绑定该组的用户自动生效，不用逐个维护。

## 模型

挂在现有的「积分配置」上（`shop_category_points_rule` + `user_zhenren_list`），和吃量比例、加积分方式走同一套缓存与回落规则。

- **档位**：ID 0 固定表示原价，不存分值，取价时实时用商品积分，所以改商品积分不需要同步档位。其余档位存整数积分，单位与 `shop_category.score` 相同，直接按积分录入，不做价格换算（2026-10-29 已确认）。
- **策略组**：包含名称、是否默认组（最多一个），以及若干「档位 + 权重」。权重按组内占比随机，不要求合计为 1。
- **用户**：白名单记录上只存 `score_group_id`。为空时走默认组。
- **取价顺序**：用户绑定的组 → 默认组 → 原价。用户绑定的组被删除，或组里没有可用档位（档位已删、权重为 0）时，往下一级回落，不会报错，也不会影响领单。
- **ID 不复用**：档位和组共用 `seq` 分配 ID。新出现的 ID 必须大于已保存的 `seq`，清空配置时 `seq` 也保留。这样删掉的组 ID 不会被新组顶替，绑定旧组的用户不会悄悄落到新组上。

整份配置以 JSON 形式存在 `shop_category_points_rule.score_config`，结构见 `ScoreConfigDTO`。

## 接入点

- `GetOrderStrategy.buildOrderRecord`：单个领任务和批量领任务都走这里。商品积分改为 `pointsRuleService.resolveScore(品类, 用户, 原价)`，结果再叠加渠道加成，写入 `order_record.order_score`。读配置出现异常时记 error 日志，并退回原价。
- 审核加积分、统计、对账读的都是落库后的 `order_score`，这些都不用改。
- Redis 读取次数：沿用 `barry_points_rule_g_{品类}` 和 `barry_points_rule_u_{品类}_{用户}` 两个 key。每次领单最多多读 2 次 Redis；没配策略组的商品只读 1 次。

## 接口

Barry（inner-client / barry-gateway-pro）：

- `POST /pointsRule/scoreConfig?shopCategoryId=`，body 为 `ScoreConfigDTO`：整份替换。校验失败时 `errorMsg` 返回具体原因。
- `GET /pointsRule` 的返回里新增 `scoreConfig`。
- `POST /user/whitelist/pointsRule` 新增 `scoreGroupId`，白名单列表也返回 `scoreGroupId`。

Phoenix BFF：

- 新增 `PUT /barry/points-rules/score-config`，body 为 `{shopCategoryId, scoreConfig}`。
- `GET /barry/points-rules` 和 `PUT /barry/user-whitelists/:id/points-rule` 透传新字段。
- `DetailResponseDTO` 新增 `ErrorMsg`，用来把 Barry 的校验提示原样返回给前端。

管理端：人工商品 → 积分配置弹窗，新增「价格策略」区，可以加减档位、加减策略组、勾选档位并配权重，实时显示概率和期望积分。用户列表新增「价格策略组」列，用户编辑弹窗可以选择策略组。

## 发布顺序

1. 执行 `barry/sql/add_points_score_group.sql`（两条 ALTER，执行前确认列不存在）。前提是 `add_points_rule.sql` 已经执行过。
2. 发布 Barry。领任务所在的进程和 barry-gateway-pro 都要发。`GetOrderStrategy` 新增了对 `PointsRuleService` 的依赖；`order-business-core` 本身就依赖 `user-service-core`，Spring 会按 `spring/spring-*.xml` 全量加载，所以能注入。
3. Phoenix BFF 的部署配置补上 `barry.url.inner.points.rule.score.config.suffix = /pointsRule/scoreConfig`。
4. 执行权限资源 SQL `phoenix/server/suffer/web-api/sql/add_points_score_group_resources.sql`。BFF 会按路由模板鉴权，没有这条资源记录时新接口会被拒绝。
5. 发布 Phoenix BFF 和管理端。

兼容性：没有配置策略组的商品，行为和原来完全一样。新版 Barry 搭配旧管理端时，保存用户积分配置会把 `scoreGroupId` 清空，效果是走默认组；上线前本来就没有组，所以没有影响。

## 测试环境待验收

1. 打开积分配置，加两个档位、两个组（标准组设为默认：原价:档位1 = 1:3；高价组：只有档位2），保存后刷新，配置能正确回显。
2. 不绑组的用户领 20 单，积分只出现原价和档位1，比例大致为 1:3。绑定高价组的用户领单，积分全部是档位2（另加渠道加成）。
3. 删除高价组并保存：该用户的列显示「组已删除，走默认」，再领单时积分走默认组。
4. 新加一个组：它的 ID 和刚删除的组不同，原先绑定旧组的用户不会被带到新组。
5. 修改商品积分（原价）后，等 shop 缓存刷新，再领单时原价档位按新积分出。

## 待确认 / 未做

- **展示与预估还是原价**：App 任务列表展示的积分（`ShopCategoryWebConvert`）、对账/工作台按分类估算的待审积分，用的仍是商品原价。如果要按期望积分展示，需要另外改。
- **原价取的是快照**：原价取的是 shop 入库时快照的 `shopCategoryScore`（原有行为）。改商品积分后，已入库的 shop 要等缓存刷新才会生效。
- **没有记录抽中的档位**：`order_record` 上没有记录这一单抽中的是哪个档位，只有最终积分。如果对账需要按档位统计，要在大表上加列，这次没做。
- **批量派单没有接入**：外部平台批量派单（`AssignmentBusinessImpl.fillScore` → `BatchAssignProcessor`）不走领任务流程，这次没有接入策略组。
