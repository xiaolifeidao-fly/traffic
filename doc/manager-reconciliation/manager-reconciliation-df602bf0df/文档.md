# 完善工作台录入、预警处置与权限交互

## 1. 任务目标

本任务仅完成「梳理需求」：在前置真实 API 对接已可用的前提下，将资金出入账对账工作台的流水、人工账户日状态、社区账户主体和差异预警做成可持久化、可处置、受权限约束的操作闭环；每次成功写入后刷新概览、维度汇总、流水、系统/人工账户状态和预警，避免继续依赖本地数组或前端重算账务金额。

本阶段只更新需求文档，不修改 `phoenix` 业务代码。动作执行前仍须确认前置后端 API 已实际合入当前分支。

### 3.2 流水录入、编辑与删除

1. `LedgerCard.tsx` 的列表和汇总均显示服务端查询结果；汇总、差异与概览不得由前端将 decimal 字符串转换为 `Number()` 后重新聚合。
2. 新增流水表单补充“账户主体”选择器，数据来自启用的账户主体接口；提交 `recordDate`、`recordType`（前端显示“入账/出款”需映射为 `INCOME`/`PAYOUT`）、`category`、`subjectId`、RMB/U 金额与手续费字符串、`remark`。
3. 现有流水编辑改为单条受控保存：进入编辑行后保存调用 `PUT /reconciliation/ledger-records/:id`，取消不提交；禁止在输入时直接改父组件结果集。创建调用 `POST /reconciliation/ledger-records`，删除经确认框调用 `DELETE /reconciliation/ledger-records/:id`。
4. 每个写按钮在请求期间禁用并显示提交态；失败保留用户输入/编辑态并用统一错误提示展示后端信息；成功后关闭对应编辑态、提示成功并刷新整个工作台。
5. 已删除或已失效记录不在默认明细中展示；若后端后续提供历史筛选，作为只读筛选能力另行接入，本任务不在前端伪造恢复动作。

### 3.3 人工账户日状态与动态社区主体

1. 系统账户状态始终只读，人工账户状态以服务端记录 ID 渲染；不能再按主体显示名匹配或生成本地 ID。
2. 新增人工状态调用 `POST /reconciliation/manual-account-statuses`；日期与 `subjectId` 是唯一自然键。服务端返回冲突时保留弹窗内容并提示“该日期和主体已有记录”，不得在列表中插入第二条。
3. 已有人工状态只能调用 `PUT /reconciliation/manual-account-statuses/:id` 更新四个金额；日期、主体和主体类型/快照不可在编辑态改写，避免违反后端“更新不得变更自然键”的约束。若需更换日期或主体，用户应新增目标记录，再按实际业务规则处理旧记录；本任务不增加人工状态删除接口。
4. “新增社区”不能仅把文本写入状态行：应先通过 `POST /reconciliation/account-subjects` 创建启用的社区主体，成功取得 `subjectId` 后再创建该日期的人工账户状态。新主体成功后刷新主体选项和工作台数据。
5. 账户主体创建所需的 `subjectCode`、排序及完整请求字段以前置后端 DTO 为准；当前前端没有可信编码生成规则，因此动作执行不得前端临时拼接或用中文名称代替 `subjectCode`。

### 3.4 预警查询与处置

1. 移除 `AccountStatusCard` 中按 5% 本地计算 `alerts` 的逻辑，改为读取服务端预警列表。列表至少展示日期、主体快照、字段、系统值、人工值、差额/差异率、阈值、状态、跟进备注、处置人和处置时间（以实际 DTO 为准）。
2. 对待处理预警提供“确认”“忽略”“修复”操作，统一调用 `PUT /reconciliation/alerts/:id/handling`，只传服务端允许的 `status` 与 `followRemark`；确认框/弹窗必须要求或允许填写跟进备注的最终必填规则，以后端 DTO 与产品确认结果为准。
3. “修复”在本任务中是预警处置状态，不隐式修改流水、人工账户状态或重跑计算；若业务要求“修复”跳转至对应记录，后端 DTO 需提供可定位的记录 ID，否则只完成状态与备注提交。
4. 预警处置成功后刷新预警和全部相关工作台数据；失败不乐观改变行状态。处置中的单行按钮禁用，避免重复提交。

### 3.5 权限交互

1. 写入口包括流水新增/编辑/删除、人工状态新增/保存、账户主体创建和预警处置；无写权限时隐藏入口或保留禁用按钮并说明原因，绝不能仅依赖前端限制，后端仍是最终鉴权方。
2. 因当前登录态不含权限资源，动作执行必须先选择并接入一个真实权限来源：优先由登录/会话接口返回可用 reconciliation action/resource 标识，或新增只读的“当前用户权限”接口并写入 `AuthUser`。在此之前不能根据 `roleName` 猜测管理员身份。
3. 由于既有后端只按 URL、不按 HTTP method 授权，若产品要求“可读不可写”，后端必须为写操作提供独立动作路径/资源，或先完成权限模型升级；仅在前端隐藏按钮不能满足权限需求。若当前后端仅授予管理员，应把所有写入口视为管理员能力，并在无授权的 403 响应时提示并刷新权限/数据状态。
4. 数据查询和只读展示应继续可用（前提是对应查询资源已授权）；加载中、空态、网络错误和 401/403 均使用现有 axios/通知约定处理，不把失败结果回退为 mock 数据。

## 4. 设计要求

1. **日期与范围：**日期参数及表单日期使用 `YYYY-MM-DD`，按 `Asia/Shanghai` 自然日传递；写后刷新保持用户当前选择的日期区间与分页/筛选，不强制跳回默认日期。
2. **金额与精度：**前端仅把金额字符串作为展示与请求值；表单做非科学计数法、合法 decimal 格式校验，但不自行累计/比较作为账务最终结论。页面展示可使用格式化函数，不能将格式化后的数值回传。
3. **类型映射：**显示层可保留中文标签；API 层集中维护枚举映射，禁止向后端传“入账”“出款”“社区”等展示文案替代受控枚举或主体 ID。
4. **刷新原子性：**任何创建、更新、删除或预警处置成功后，由 Hook 触发一次完整刷新；刷新失败需保留已成功的服务端写入事实并显示“操作成功，但刷新失败”，提供重试入口，不能回滚为旧本地数据。
5. **并发与编辑：**开始编辑后若外部刷新到达，应避免无提示覆盖草稿；提交时若后端返回冲突/记录不存在，保留草稿并提示用户刷新后处理。具体乐观锁版本字段仅在后端 DTO 实际提供时接入。
6. **国际化与可访问性：**新增用户可见文本通过现有 `useLocale()` 及全部语言资源管理；图标按钮提供 Tooltip/可读标签，危险删除和不可逆处置必须二次确认。

## 5. 约束与非目标

1. 本任务不实现后端 reconciliation Handler、Repository、表结构、日汇总或重跑逻辑；这些属于前置 `reconciliation-backend-c031403fbb` 的交付范围。
2. 不修改系统账户状态；不在浏览器端重算预警、汇总、差异率或账务金额。
3. 不将流水/账户主体/人工状态保存到 localStorage、sessionStorage 或 mock 文件；也不使用 `fetch` 绕过 `@/utils/axios`。
4. 不通过前端角色名硬编码权限，也不以隐藏按钮替代服务端资源鉴权。
5. 不臆定预警状态枚举、跟进备注必填规则、主体编码规则、账户主体创建字段或流水变更后的自动重算时机。

## 6. 验收标准

1. 工作台首次加载、变更日期区间、点击刷新均从真实 `/reconciliation` 查询接口取得概览、维度、流水、系统/人工账户状态和预警；断网、空数据、401/403/业务错误不展示或恢复 mock 数据。
2. 流水新增表单可选择启用主体并提交服务端要求的字段；新增、单条编辑、删除均调用对应 API，失败不改当前服务端列表，成功后完整刷新并使概览、明细、差异一致。
3. 所有金额请求保持 decimal 字符串；受影响组件中不存在以 `Number()` / `reduce()` 对流水执行账务汇总或以本地 5% 阈值生成预警的逻辑。
4. 人工账户状态可按日期与主体新增；重复自然键被明确提示。已有记录编辑时不能修改日期、主体和主体类型，成功后只显示服务端刷新结果。
5. 选择“新增社区”会先成功创建账户主体、获得服务端 `subjectId`，再创建人工账户状态；任一步失败均不会把假主体或假状态插入页面。
6. 预警来自服务端；确认、忽略、修复均只提交允许的处置字段，展示提交态、失败反馈和成功后的刷新，不修改预警计算值。
7. 写入口依据真实权限数据隐藏或禁用；无权限用户无法触发写请求，且直接调用 API 仍由后端拒绝。若仅有 URL 级权限，读写分离需求必须由独立资源路径或权限模型改造实现。
8. 新增 API DTO、Hook、组件改造和 i18n 文案通过管理端既有 TypeScript/lint/build 校验；至少覆盖一次创建、更新、删除、状态冲突、权限拒绝、预警处置成功与刷新失败后的重试验证。

## 7. 风险与待确认

1. **前置代码仍不可见：**当前工作树没有 reconciliation 后端包，无法核验实际 JSON 字段、枚举、分页响应或权限资源 URL。动作执行开始前必须确认 `reconciliation-backend-c031403fbb` 的代码已合入；若仍缺失，应阻塞实现而非以 mock 契约替代。
2. **权限来源未定：**现有登录响应和 `AuthUser` 没有权限集合。需要确认由登录接口扩展、独立当前用户权限接口提供，还是先将工作台写权限固定为可验证的后端资源能力；不能用 `roleName` 推断。
3. **读写分权无法用同一路径解决：**后端鉴权不区分 HTTP method。若运营人员应只读，须确认独立写操作路径还是权限模型改造，该决策是本任务权限交互的前置。
4. **新社区编码与创建顺序：**前置接口要求主体编码且主体先于人工状态创建，但当前代码没有编码规则或 DTO。须确认后端是否生成编码、是否允许仅传名称/类型，及创建失败后的业务提示。
5. **预警“修复”语义和状态机：**需确认 `CONFIRMED`、`IGNORED`、`FIXED` 等实际状态值、备注是否必填，以及重跑后差异仍存在/已消失时的状态迁移。前端只能展示并提交后端最终枚举。
6. **写后重算：**前置文档默认流水和人工状态写入不在 HTTP 请求内隐式触发重算。若财务需要实时重算，需单独定义受控重跑 API、耗时反馈和审计，不能由前端自行计算。
