# uid 维度提交率门槛拦截取单与配置化改造

- 需求键：req-1787757810015
- 所属项目：流量项目（program_id = 2）
- 里程碑：做单监控一期（manual-monitor-v1）
- 涉及模块：barry 分发（barry-assignment）、管理端工作台（manager-workbench）
- 主负责人：未指定

## 一、需求背景与目标

现有 uid 维度的分配限制只看账号质量（粉丝数、作品数、互动率），无法识别「持续拿单但不提交」的 uid。这类 uid 会长期占用候选池，压低整体交付效率。

本需求引入**提交率门槛**：按 `userId + uid + shopProperty(type)` 统计短窗口内的取单数与提交数，计算提交率；在 **fetchInit 建池阶段**，对命中配置链接关键字的候选，提交率不达标的 uid 不参与分配。门槛支持品类全局与按用户两层配置，由管理端「分配策略 - uid 维度」页维护。

## 二、范围与不做的事

### 范围内
1. 取单与提交两侧新增 Redis 计数埋点，按 10 分钟时间片对齐。
2. uid 维度提交率规则的数据模型与内管接口，支持品类全局 + 用户级两层。
3. fetchInit 建池阶段新增提交率过滤器。
4. 管理端 uid 维度页新增提交率配置（全局 + 用户级）。
5. 灰度验证与拦截可观测性。

### 明确不做
1. **不拦拿单实时链路**：`AssignDimensionFilter`（fetchUserOrder 链路）不做提交率判定，本次只拦 fetchInit。
2. **不改动既有提交计数**：`OrderCache.incrSubmit`（key `barry_order_submit_num_<date>_<userId>_<uid>_<shopTypeId>`、TTL 24h）保持原样，新计数独立新增，避免影响既有依赖。
3. 不调整现有 uid 维度的粉丝数 / 作品数 / 互动率规则语义。

## 三、关键约束与业务规则

### 3.1 统计口径
- 统计维度：`userId + uid + shopProperty 的 type`。取单侧的 type 与提交侧 `order_record.tag` 同源（tag 就是落单时写入的 `property.type`）。
- **时间片对齐**：key 后缀为 `yyyyMMdd + 10 分钟片号`（如 `1730`、`1740`），取单与提交计数使用完全相同的片，TTL 统一 20 分钟。此方案是为解决「两个计数有效期如何保持一致」——分子分母同片同生共死，不会出现单边过期导致提交率虚低。
- Key：`barry_uid_fetch_num_<yyyyMMdd>_<片号>_<userId>_<uid>_<type>`、`barry_uid_submit_num_<同后缀>`。

### 3.2 判定规则（fetchInit）
按顺序判定，任一条件命中即放行：
1. uid 维度总开关关闭 → 放行（**提交率规则随总开关一并失效**）。
2. 提交率规则未开启，或未配置链接关键字 → 放行。
3. 候选链接（`property.url`）未命中配置的关键字 → 放行。
4. 同一时间片内取单数 < 最小样本量（**默认 5**）→ 放行。这是防误杀的兜底：避免「取 1 单还没提交就被判 0%」。
5. 提交率 = 同片提交数 / 同片取单数，低于配置门槛 → **过滤该候选**，打 debug 日志。

### 3.3 配置生效关系
- 匹配对象由分配策略里的配置决定：配了什么关键字就用什么匹配 `property.url`；计数维度固定用 `shopProperty` 的 `type`。
- 同一 `(shopCategoryId, userId)` 存在用户级规则时**整体覆盖**全局，不存在则回落全局。
- 生效时延：维度开关 1 分钟、规则 5 分钟（沿用现有内存快照刷新节奏）。

### 3.4 非功能约束
- 建池过滤器运行时**零查库**，只读内存快照与 Redis；候选 `shopAssemble` 仍只查询一次，链接与 type 复用同一次结果。
- 埋点与过滤的异常只记日志，不影响取单、提交、建池主流程。

## 六、验收标准

1. 同一时间片内取单一次、提交一次，`barry_uid_fetch_num_` 与 `barry_uid_submit_num_` 对应 key 各 +1 且 TTL 一致；type 为空不写 key。
2. 提交率规则的全局与用户级配置均可在管理端 uid 维度页增删改查并正确回显；用户级为空时回落全局并有提示。
3. 建池阶段：样本量达标且提交率低于门槛的 uid 被过滤且有日志；样本量不足、链接未命中关键字、总开关关闭三种情况均放行。
4. uid 维度总开关关闭后，建池结果与改造前完全一致（回滚路径可用）。
5. 拿单实时链路 `AssignDimensionFilter` 行为不变；`OrderCache.incrSubmit` 的 key 与 TTL 不变。
6. 埋点与过滤逻辑的异常不影响取单、提交、建池主流程。
7. 表结构变更 SQL 已提交至 `barry/sql/`。
8. 产出一轮真实或准真实数据的灰度验证记录。

## 七、待确认问题

1. **最小样本量默认值 5** 为估算取值（10 分钟窗口内取单量普遍不高，5 既能挡住极小样本的误判，又不至于让规则失效）。若有线上取单频次数据，可据此调整默认值。
2. 最低提交率门槛的推荐默认值尚未确定，当前按「不配置即不生效」处理，需运营给出首批品类的建议阈值。
