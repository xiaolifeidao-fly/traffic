## 一、需求背景与目标

前序任务已经完成 `SingleAssignFinishMonitor` 所属 `FINISH_ASSIGNMENT` 队列的待检测数量、按商品类目的日消费计数、Barry Inner / Phoenix 代理，以及新管理端工作台展示。

本轮在现有实现上增加 `UserAssignDelayMonitor` 所属 `DELAY_ASSIGNMENT` 队列监控，并统一工作台文案与展示结构：

1. 在现有独立“待检测数量”块中，同时展示：
   - `FINISH_ASSIGNMENT`：分配延迟待检测数量。
   - `DELAY_ASSIGNMENT`：用户延迟待检测数量。
2. 两种待检测数量都按商品分组查询：通过 `cluster_type + mapping_key=shopGroupId` 唯一取得 `cluster_config_id`，展开全部 Topic 并汇总 Redis ZSET `ZCARD`。
3. 将现有“今日已消费 / 消费速度”文案改为“今日分配延迟已检测 / 检测速度”。
4. 增加“今日用户延迟检测数量 / 检测速度”，消费点为 `UserAssignDelayMonitor.handleMsg`，计数和速度机制与 `SingleAssignFinishMonitor` 一致。
5. 两种检测速度都使用现有真人 / 低价卡片的 `shopCategoryIds` 作为查询范围。

## 三、关键约束与已确认口径

1. **分配延迟队列**：`SingleAssignFinishMonitor`，集群类型 `FINISH_ASSIGNMENT`。
2. **用户延迟队列**：`UserAssignDelayMonitor`，集群类型 `DELAY_ASSIGNMENT`。
3. **待检测查询**：两种集群类型都按 `cluster_type + mapping_key=shopGroupId` 从 `cluster_mapping` 唯一取得 `cluster_config_id`，通过 `ClusterConfigService.findById/getClusterTopics` 展开全部 Topic，使用 `RedisService.getZCards` 汇总 ZCARD。
4. **分配延迟检测计数**：现有 `SingleAssignFinishMonitor` 日计数继续保留。
5. **用户延迟检测计数**：`UserAssignDelayMonitor.handleMsg` 成功加载非空 `AssignmentDTO` 后立即 +1，再执行原有 `isPending` 与 `pushDelayQueue`。
6. **日计数维度**：按 `shopCategoryId + yyyyMMdd`；用户延迟与分配延迟使用不同 Redis key 前缀。
7. **TTL 与速度**：两类日计数 TTL 均为 25 小时；检测速度均为“今日累计检测数 ÷ 当日已过分钟数”，单位“条/分钟”。
8. **重投口径**：同一消息因原逻辑再次投递并再次消费时再次计数，反映消费者真实检测吞吐。
9. **接口兼容**：现有 `pendingDetectionCount`、`consumedCount`、`consumePerMinute` 字段继续兼容，并明确映射为分配延迟指标；新增显式分配延迟字段与用户延迟字段。
10. **主链路保护**：新增 Redis 写入和读取必须捕获异常，不能影响原有分发、延迟消费和重新入队。

## 七、逐条任务说明

### 1. Barry 按商品分组汇总 DELAY_ASSIGNMENT 用户延迟待检测消息数

**目标**  
在现有分配延迟待检测数量之外，按商品分组统计 `UserAssignDelayMonitor` 所属 `DELAY_ASSIGNMENT` 队列当前待检测消息数。

**范围**

- 将现有固定 `FINISH_ASSIGNMENT` 的队列计数 helper 参数化为 `clusterType + shopGroupId`。
- 使用 `ClusterType.DELAY_ASSIGNMENT` 与 `shopGroupId` 唯一查询 ClusterConfig。
- 复用 `getClusterTopics` 和 `RedisService.getZCards`，汇总全部 Topic ZCARD。
- 保留原 `FINISH_ASSIGNMENT` 结果并补用户延迟结果，不重复实现 Pipeline。

**验收标准**

- 每个商品分组的用户延迟待检测数等于其 `DELAY_ASSIGNMENT` 全部 Topic 的 ZCARD 合计。
- 同一查询同时获得分配延迟待检测量和用户延迟待检测量。
- Topic 不存在、映射为空或 Redis 异常时对应指标返回 0，不影响另一类指标。
- 原分配延迟待检测数量无回归。

### 2. UserAssignDelayMonitor 按商品类目维护日检测计数

**目标**  
按商品类目统计今日 `UserAssignDelayMonitor` 已经消费检测的消息数量，并支持计算检测速度。

**范围**

- 在 `AssignmentSupportCache` 增加独立用户延迟 key 前缀的 INCR、TTL 自愈和批量读取方法。
- 在 `UserAssignDelayMonitor.handleMsg` 成功加载非空 `AssignmentDTO` 后计数一次，再执行原有 Pending 判断。
- 复用分配延迟计数的日期格式、25 小时 TTL、批量读取和异常保护机制。

**验收标准**

- 同一商品类目每消费一条有效 `DELAY_ASSIGNMENT` 消息，今日用户延迟检测数 +1。
- Assignment 不存在时不计数；消息再次投递并再次消费时再次计数。
- 用户延迟和分配延迟使用不同 key，数据互不覆盖。
- Redis 异常不影响 `isPending` 和 `pushDelayQueue`。

### 3. Barry Inner 扩展分配延迟与用户延迟双指标

**目标**  
在现有两个工作台接口中返回两类队列待检测量，以及两类按商品类目的检测数量和检测速度。

**范围**

- 扩展 `/workbench/dashboard/pending-detection-count`：总计与 `groupList` 均增加分配延迟待检测数和用户延迟待检测数。
- 保留现有 `pendingDetectionCount/total` 兼容字段，并映射为分配延迟待检测数。
- 扩展 `/workbench/dashboard/delay-assignment-count`：增加分配延迟已检测数 / 检测速度、用户延迟检测数 / 检测速度。
- 保留现有 `consumedCount/consumePerMinute` 兼容字段，并映射为分配延迟指标。
- 两套检测速度使用同一个当日已过分钟数，批量读取两类商品类目日计数 key。

**验收标准**

- 同一组 `shopGroupIds` 返回两类待检测数量及分组明细。
- 同一组 `shopCategoryIds` 返回两类今日检测数和条/分钟检测速度。
- 旧字段数值与新增分配延迟显式字段一致。
- 任一类计数缺失时返回 0，另一类结果不受影响。

### 4. Phoenix Suffer 透传分配延迟与用户延迟指标

**目标**  
让新管理端通过现有 Phoenix 接口获得 Barry 新增的双队列与双检测指标。

**范围**

- 扩展 Go DTO 中待检测总计、分组明细和休眠类目明细字段。
- 复用现有 `PendingDetectionCount`、`DelayAssignmentCount` Service 与 Handler，不新增路径。
- 更新代理测试，覆盖新字段反序列化和旧字段兼容。

**验收标准**

- 两条现有 Phoenix API 完整透传两类指标。
- Phoenix 不二次计算检测速度或队列数量。
- 旧字段和旧调用保持兼容。
- Barry 缺少新增字段时按零值兼容，不影响页面其他指标。

### 5. 工作台展示分配延迟与用户延迟双指标

**目标**  
在同一工作台区域清晰对比两类延迟队列的积压与今日检测能力。

**范围**

- 待检测独立块同时展示“分配延迟待检测数量”和“用户延迟待检测数量”，分组明细增加两列。
- 将现有“今日已消费 / 消费速度”改为“今日分配延迟已检测 / 检测速度”。
- 在相同休眠延迟区域新增“今日用户延迟检测数量 / 检测速度”。
- 真人 / 低价卡片继续使用各自 `shopCategoryIds`，不增加额外查询范围。
- API 类型、加载态和错误降级同步支持新增字段。

**验收标准**

- 待检测块在同一商品分组范围内同时展示两类待检测数量。
- 真人与低价卡片准确显示“今日分配延迟已检测 / 检测速度”。
- 真人与低价卡片准确显示“今日用户延迟检测数量 / 检测速度”。
- 页面不再出现旧文案“今日已消费 / 消费速度”。
- 一类指标异常或为空时展示 0 / `-`，不影响另一类指标和其他工作台卡片。
