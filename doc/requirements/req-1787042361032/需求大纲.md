# 新管理端-增加人工分发接口速度监控界面

需求键：req-1787042361032 ｜ 项目：流量项目（program_id=2） ｜ 起始阶段：development
主负责人：未指派

## 一、需求背景与目标

barry 的做单用户在调用「获取任务」接口时，经常出现取不到任务的情况，目前没有任何实时观测手段，无法判断是分发池空、策略过滤太严，还是某个用户/某个 uid 被单独卡住。

目标：在 barry 取单入口埋点，按「用户」和「用户+uid」两个维度统计短时间窗口内的**取到任务次数**与**无任务次数**，并在新管理端「人工」菜单下展示对应的做单速度，用于快速定位分发异常。

## 二、范围与不做的事

范围内：
- barry：`fetchUserOrder` 入口埋点，写 Redis 计数 key（用户维度 2 个、用户+uid 维度 2 个），key 带可配置有效期（默认 2 分钟）。
- barry：gateway-inner 新增监控查询接口，按 userId 批量、按 userId+uid 批量返回命中/无任务次数与速度。
- phoenix suffer：新增 Barry 代理接口与权限资源。
- 新管理端：「人工」菜单下新增「用户做单监控」页面（app_user 分页列表 + 取到/取不到数量 + 速度）；「做单明细」页扩展 uid+userId 维度的速度列。
- 二期追加：速度按各 key 自己的剩余有效期反推「已发生时间」计算，并在两个页面展示「已持续时间」。

不做（已与用户确认）：
- 不统计除返回码 3 以外的失败（参数非法 5、超上限 1、并发锁 2、渠道维护 6 都不计入未命中）。
- 不做历史时序存储与曲线（只看当前窗口的瞬时速度）。
- 不用 scan 反查 Redis 去补「明细里没有记录」的 uid 行。
- 不监控批量取单入口 `UserBatchOrderService`。
- 不改动分发策略本身、不新增告警推送。

## 三、关键约束

- 「取不到任务」的口径**只算返回码 3（无任务，请稍后再试）**，其余错误码不计入任何计数。
- 计数只落 Redis，不建表；key 过期即丢弃，属于瞬时观测数据。
- **TTL 必须保证一定设置成功**：先 `set(key, "0", "NX", "EX", window)` 原子建 key 带过期，再 `incr`；同时在 incr 后兜底判断 `ttl == -1` 则补 `expire`，避免服务重启或 incr/expire 之间中断导致 key 永不过期。
- 窗口时长走配置，默认 120 秒；barry 侧配置项与前端展示的窗口值要一致。
- 埋点必须无侵入、异常不可影响取单主流程（try/catch 兜底 + 开关）。
- 分页列表要批量读 Redis（pipeline），不能每行一次 `get`。
- 平均速度必须用「窗口时长 − 该 key 剩余有效期 = 已发生时间」作为分母；hit 与 miss 是两个独立 key、创建时间可能不同，各自的速度必须用**各自** key 的 TTL 反推，不能共用一个 elapsed。
- Phoenix 侧查询类接口统一走 barry `gateway-inner`，遵循 `phoenix/.claude/skills/backend-development`。
- 新增管理端接口必须补权限资源 SQL，遵循 `phoenix/.claude/skills/add-permission-resources`。

### 任务 1 barry 取单入口埋点用户与 uid 维度取单/无任务计数
- 目标：在 `AbsUserOrderService.fetchUserOrder` 统一出口按结果写 4 类 Redis 计数。
- 范围：新增 `OrderFetchMonitorCache`（放 `business/order/support`），key 设计
  `barry_order_fetch_hit_user_{userId}` / `barry_order_fetch_miss_user_{userId}` /
  `barry_order_fetch_hit_uid_{userId}_{uid}` / `barry_order_fetch_miss_uid_{userId}_{uid}`。
  命中：`fetchOrderByRequest` 返回非空；未命中：**仅**走 `buildError("3", ...)` 这一条分支，其余提前返回的错误码不计数。
  计数写入用 `set(key,"0","NX","EX",window)` + `incr`，并在 incr 后校验 `ttl == -1` 时补 `expire`，保证重启或中途异常不会留下永不过期的 key。
  配置：`user.order.fetch.monitor.window.seconds:120`、`user.order.fetch.monitor.enabled:true`；埋点整体 try/catch，异常只打日志。
- 验收：取到任务、无任务各触发一次后，对应 4 个 key 的计数与 TTL 正确；窗口到期自动清零；返回码 1/2/5/6 时不产生任何 key；杀掉服务后重启再取单，key 仍带 TTL（无永久 key）；关开关后不再写 key。

### 任务 6 barry 监控接口按 key 各自剩余有效期计算已持续时间与平均速度（manual-monitor-1d53ced763）
- 目标：修正速度分母口径，并把「已持续时间 / 剩余有效期」作为接口字段暴露出去。
- 现状：`OrderFetchMonitorController.calculateElapsedSeconds` 取 hit、miss 两个 key TTL 的**最小值**算出单一 `elapsedSeconds`，hitSpeed 与 missSpeed 共用它；两个 key 创建时间不同（例如 miss key 刚新建、hit key 已过大半窗口）时，其中一个维度的速度会算偏。
- 范围：`barry-gateway/barry-gateway-inner-client/.../controller/order/OrderFetchMonitorController.java` 改为逐 key 取 TTL：`hitRemainingSeconds`/`missRemainingSeconds`（key 不存在记 0），`hitElapsedSeconds = window − hitRemaining`、`missElapsedSeconds = window − missRemaining`，速度各自用对应 elapsed 作分母；`elapsedSeconds` 保留为两者最大值，作为该行的「已持续时间」并保持字段向后兼容。`.../model/order/OrderFetchMonitorModel.java` 增加 hitRemainingSeconds、missRemainingSeconds、hitElapsedSeconds、missElapsedSeconds 四个字段。继续使用现有 `RedisService.getTtls` / `getStringValues` 批量读取，不新增 Redis 往返。
- 验收：hit 与 miss key TTL 不同的场景下两个速度分别用各自 elapsed 计算并可复核；key 不存在时 remaining=0、elapsed=0、速度=0 且不报错；elapsedSeconds = 窗口 − 两个 key 中较大的剩余有效期；接口 Redis 往返次数不增加；原有字段含义不变。

## 六、验收标准（需求级）

1. barry 取单命中与「无任务(码 3)」在用户与 uid 两个维度均有计数，key 有效期由配置控制，默认 2 分钟，且任何情况下不会出现无 TTL 的残留 key。
2. 管理端「人工」下新增「用户做单监控」菜单，可分页看到 app_user 列表及两个数量与速度。
3. 「做单明细」页可看到 uid+userId 维度的两个数量与速度。
4. 埋点异常、Redis 不可用时取单主流程不受影响。
5. 新增接口均有权限资源记录，未授权角色不可访问。
6. 用户维度与 uid 维度的平均速度均以「窗口 − 该 key 剩余有效期」为分母，且两个页面都能看到该行的已持续时间。

## 八、已确认结论（历史）

- 未命中口径只算返回码 3。
- 采用固定窗口（首次建 key 设 TTL，过期清零，速度 = 计数 ÷ 已过窗口时长），并额外要求 TTL 设置的健壮性。
- 「做单情况菜单」= 现有「人工 → 做单明细」页面。
- 不做 Redis scan 反查缺失 uid 行。
- 不监控批量取单入口。
- 里程碑与模块新建，已落库为 manual-monitor-v1 / manual-monitor。
