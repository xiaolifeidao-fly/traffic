# 工作台实时上号数 Redis 心跳统计改造（req-1788421430587）

## 摘要

新管理端工作台「实时上号」卡片当前统计的是「窗口内出过单」的用户与 uID，用户轮询取单却没抢到任务时不会落 `order_record`，该 uID 完全统计不到。本需求改为 Redis 心跳口径：只要在 120 秒窗口内调用过 barry 取单入口，该 uID 即视为在线。改造范围只在 barry 内部（取单入口埋心跳 + 工作台在线统计换数据源 + `/user-online-overview` 切换），旧 SQL 口径保留给 `/user-overview`，phoenix 与前端零改动。验收口径：只轮询、始终取不到任务的 uID 必须能被统计到，顶部数字与明细表合计自洽，`/user-overview` 返回值逐字段不变。

## 需求背景与目标

- 现状：`WorkbenchDashboardServiceImpl.userOverview`（101-118 行）通过 `OrderRecordRepository.summarizeWorkbenchOnlineUsers`（16-22 行）按 `order_record.created_time >= 窗口起点` 聚合 `COUNT(DISTINCT ext_user_id)`，默认窗口 120 秒。
- 问题：这是「出单」口径而非「在线」口径。没抢到单、个人池为空、被前置校验拦截的 uID 不产生订单记录，在卡片上直接消失，导致实时上号数被低估。
- 目标：把在线判定改为「窗口内调用过取单接口」，用 Redis 记录 userId + uID 的心跳时间戳，让工作台反映真实上号规模。

## 范围与不做的事

### 做

- 在 barry 统一取单入口写入 uID 在线心跳（Redis ZSET）。
- 新增基于 Redis 的在线统计查询，替换 `/user-online-overview` 的在线人数、在线账号数与用户明细列表数据源。
- 补齐 `RedisService` 缺失的 ZSET 能力（`zcount`、`zremrangeByScore`、无 offset/count 的 `zRangeByScore` 重载）。

### 不做

- 不修改旧 SQL 口径：`summarizeWorkbenchOnlineUsers` 与 `/user-overview` 行为完全保持不变，供 Kakrolot 等既有调用方继续使用。
- 不加口径切换开关（明确确认不需要）。
- 不改 `WorkbenchUserOverviewDTO` 字段结构，因此 phoenix 与前端 `client/manager` 不做任何代码改动。
- 心跳来源只认取单入口，不给提交任务、保活等其它接口埋点。
- 不改工作台前端展示与样式。

## 关键约束

- **在线口径**：进入 `fetchUserOrder` 且 `uuid` 非空即记心跳——取到单、未取到单、被前置校验拦截（渠道未配置、超上限、并发锁未获取）都算在线；`uuid` 为空（用户参数非法）跳过。
- **窗口**：默认 120 秒，沿用现有 `windowSeconds` 参数与 `statisticsWindowSeconds` 校验。`ZADD` 对已存在 member 覆盖 score，同一 uID 每次取单只刷新时间戳。
- **既定行为（非缺陷）**：客户端取单轮询间隔若超过 120 秒，该 uID 会滑出在线统计。验收按此口径判定。
- **心跳写入不得影响主流程**：整体 try-catch，失败只 `log.warn`，Redis 异常时取单接口行为不变。
- **Redis key 契约**：`barry_online_uid_{userId}`（member = uid）、`barry_online_user`（member = userId），score 为当前时间戳；两条任务必须使用一致的 key 名与时间单位。
- **过期与清理**：`barry_online_uid_{userId}` 由写入侧加 TTL 兜底（`ttl < 0` 时设 3600 秒），彻底离线用户靠 TTL 回收；`barry_online_user` 不设 TTL，由查询侧 `ZREMRANGEBYSCORE` 清理，ZSET 清空后 Redis 自动删 key。
- **性能约束**：写路径每次取单增加 2 次 `ZADD`；读路径为 1 次清理 + 1 次 `ZRANGEBYSCORE` + `N/500` 次 `eval`（Lua 批量 `ZCOUNT`）+ 1 次 `findByIds` 批量查询，避免逐用户往返。按高峰期在线用户数千级设计；若实际达到万级，需追加 5-10 秒结果短缓存，实现时预留口子。
- **Redis 为内存态**：重启或清库后窗口内数据会短暂偏低，属可接受范围。

## 验收标准

### 心跳写入（任务 1）

- 同一账号的一个 uID 持续调用 `/task/get`，即使始终返回「无任务,请稍后再试」，`ZSCORE barry_online_uid_{userId} {uid}` 仍存在并随每次调用刷新。
- 被前置校验拦截的场景（超上限、渠道未配置等）同样写入心跳。
- `ZSCORE barry_online_user {userId}` 随取单刷新；`TTL barry_online_uid_{userId}` 返回正值。
- Redis 不可用或心跳方法抛异常时，取单接口行为不变、正常返回，仅打出 warn 日志。
- 单条取单与批量取单（`FullTaskController` 走的 `UserBatchOrderService`）均能写入心跳。

### 在线统计与接口切换（任务 2）

- 一个 uID 只轮询取单、始终没取到单，工作台「实时上号」在 120 秒窗口内能统计到它，明细表出现对应用户行；停止轮询超过 120 秒后从统计中消失。
- 顶部「在线人数 / 在线账号数」与展开明细表的行数、账号数合计完全一致（`onlineAccountCount` = 各明细行之和，`onlineUserCount` = 明细行数，计数为 0 的用户被过滤）。
- `/user-overview` 返回值与改造前逐字段一致。
- 明细行 username / channel 正确，排序保持在线账号数倒序、userId 升序；前端 `ManagerDashboardPanel` 明细表及其关联的取单 hit/miss 监控正常显示，phoenix 未做任何代码改动。
- 免登录变体 `/barry/public/workbench-dashboard/user-online-overview` 正常返回聚合数字。
- 多次刷新工作台后 `ZCARD barry_online_user` 与实际在线用户数一致，不随时间无限增长。

## 待确认问题

- 高峰期同时在线用户数量级尚未确认。当前按「数千级」设计；若实际达到万级，需在统计侧追加 5-10 秒结果短缓存，实现时应保留扩展口子。
- 客户端取单轮询的实际间隔未确认。若存在长于 120 秒的间隔，在线数会偏低，届时需要重新讨论窗口取值或补充心跳来源（本期不做）。
