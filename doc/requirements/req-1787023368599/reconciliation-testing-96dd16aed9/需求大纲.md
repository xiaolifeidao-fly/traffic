# 休眠延迟计数与展示的准确性验证

- 任务键：reconciliation-testing-96dd16aed9
- 所属需求：req-1787023368599 工作台增加-当前进入休眠延迟的单子有多少

## 一、任务目标

验证休眠延迟去重计数在真实分发链路下不漂移，且 barry-inner 接口与管理端工作台的展示口径一致、异常可降级。

## 二、范围与不做的事

范围内：
- barry 分发链路的进入/退出休眠计数验证
- 去重与异常自愈验证
- barry-inner 接口参数边界验证
- 管理端两张卡与类目明细的一致性、降级验证
- 记录验证结果作为上线验收依据

不做：
- 不覆盖分发策略本身的正确性（既有能力，不在本需求范围）
- 不做性能压测与容量评估
- 不覆盖历史趋势（本需求不做该能力）

## 四、实现要点（验证设计）

1. **主链路**：构造单子达到分发上限 → 进入休眠 → 延迟消息消费 → 退出休眠的完整场景，逐步对比类目集合 `SCARD` 与 `barry_assignment_delay_key_*` 的实际存量。
2. **去重**：对同一 `assignmentId` 触发多次 `doDelay`（走 `AssignProcessor.java:149` / `:184` 路径），确认 `SCARD` 不增长；多次移除不产生负数。
3. **BATCH 隔离**：走 `AssignType.BATCH` 分发，确认不计入类目集合。
4. **异常自愈**：分别验证 `delay.assign.monitor.flag=false`、Redis 短时不可用、进程重启三种情况下计数不虚高、不永久残留（TTL 生效）。
5. **接口边界**：`shopCategoryIds` 传多类目 / 空 / 未知 id 三种情况的返回。
6. **管理端一致性**：两张卡类目隔离、明细列各行合计与顶部指标一致、接口失败时降级为 0 且卡片其余内容正常。
7. 结果记录成可追溯的验证报告。

## 五、前置依赖

## 六、验收标准

1. 类目集合 `SCARD` 与 `barry_assignment_delay_key_*` 的实际存量一致。
2. 重复投递、消息丢失、消费者关闭等异常场景下不出现数字虚高或永久残留。
3. barry-inner 接口在多类目、空参、未知类目下返回符合预期。
4. 管理端两张卡展示值与 inner 接口返回一致，类目明细合计与顶部指标一致。
5. 验证结果有记录，可作为上线验收依据。
