## 一、任务目标

在 phoenix 新管理端后端（Go / suffer）新增一个代理接口，把 barry-inner 的休眠延迟量透传给管理端前端，与现有工作台卡片走同一套数据通道。

## 二、范围与不做的事

范围内：
- barry inner 路径常量与配置项
- suffer barry service 层代理方法与 DTO
- web-api 路由注册

不做：
- 不改动现有 `/barry/workbench-dashboard/*` 接口
- 不在 Go 侧直连 barry 的 Redis 或数据库
- 不做缓存层与聚合计算

## 四、实现要点

1. `helpers.go` 新增常量：
   ```go
   barryInnerWorkbenchDashboardDelayAssignmentCountPath = "barry.url.inner.workbench.dashboard.delay.assignment.count.suffix"
   ```
   并补上对应的配置项值（指向 barry 的 `/workbench/dashboard/delay-assignment-count`）。
2. `workbench_dashboard_statistics_service.go` 新增 `DelayAssignmentCount(ctx, query)` 方法，照 `ManualSpeed` 写法：
   - `DetailResponseDTO[barryDTO.WorkbenchDelayAssignmentCountDTO]`
   - `buildValues("shopCategoryIds", query.ShopCategoryIDs)`
   - `!response.Success || response.Data == nil` 时用 `responseError(...)` 返回明确错误
3. DTO 落 `suffer/service/barry/dto`，结构对齐 barry 返回：`total` + `categoryList`（`shopCategoryId` / `categoryName` / `categoryCode` / `count`）。
4. `transaction_handler.go` 的 `registerTransactionRoutes` 中注册：
   ```go
   engine.GET("/barry/workbench-dashboard/delay-assignment-count", h.getWorkbenchDelayAssignmentCount)
   ```
   Handler 用 `c.ShouldBindQuery` 绑定 `WorkbenchDashboardMetricQueryDTO`（已含 `ShopCategoryIDs`），失败返回「参数错误」，成功走 `commonRouter.ToJson`。

## 五、前置依赖
