## 一、任务目标

在 barry 侧用 Redis 维护一个以 `shop_category_id` 为维度的**休眠单子集合**，去重反映「当前有多少单子因达到分发上限而处于休眠延迟中」，作为后续 inner 接口与管理端展示的数据源。

## 二、范围与不做的事

范围内：
- `AssignmentSupportCache` 新增按类目的集合读写能力
- 进入休眠时写入、退出休眠时移除
- TTL 兜底与异常隔离

不做：
- 不修改分发策略、分发上限规则（`getLimitNum` / `isLimit`）
- 不修改延迟队列（`barry-jedis` `queues/delay`）本身的实现
- 不统计 BATCH 分发链路
- 不做历史趋势、留痕、落库

## 四、实现要点

1. 在 `AssignmentSupportCache` 新增：
   - key 构造 `barry_assign_delay_category_{shopCategoryId}`
   - `addDelayCategory(Long shopCategoryId, Long assignmentId)` → `SADD` + 刷新集合 TTL
   - `removeDelayCategory(Long shopCategoryId, Long assignmentId)` → `SREM`
   - `getDelayCategoryCount(Long shopCategoryId)` → `SCARD`
   - 批量取数方法供 inner 接口使用（多类目一次取）
2. **写入点**：`AssignProcessor.assignByAssignment`，在 `assignmentSupportCache.delay(assignmentDTO.getId(), assignConfigDTO.getExpireTimes())`（`:110`）旁调用 `addDelayCategory(assignmentDTO.getShopCategoryId(), assignmentDTO.getId())`。仅非 BATCH 分支执行，与既有 `:112` 的 `AssignType.BATCH` 判断保持一致。
3. **移除点**：
   - `UserAssignDelayMonitor.handleMsg` 处理完成后按 `assignmentDTO.getShopCategoryId()` 调用 `removeDelayCategory`
   - `DelayAssignProcessor.repairAssign` 中 `cancelDelay` 处同步移除
4. **去重天然性**：因为用 `SET` 而非 `INCR`，`AssignProcessor.java:149`/`:184` 的重复 `doDelay` 不会造成重复计数；重复 `SREM` 也不会造成负数。
5. **TTL 兜底**：集合 key 设置 TTL（建议与 `expireTimes` 量级对齐并在每次 `SADD` 时续期），保证消息丢失或 `delay.assign.monitor.flag=false` 时残留数据会自然过期，不会永久偏高。
6. **异常隔离**：所有新增 Redis 读写包 try-catch 并记日志，异常不向上抛，绝不阻塞或中断分发主链路。
7. `shopCategoryId` 为空时跳过计数，不抛异常。
