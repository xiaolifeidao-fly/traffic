## 一、需求背景与目标

barry 的分发任务在达到分发上限后会被投入 Redis 延迟队列做延迟检测，这段时间内单子处于「休眠」状态、不参与分发。目前无法观测某一商品类目下当前有多少单子处于休眠延迟中，出现「有单子却拿不到」时缺少直接依据。

目标：
1. 在 barry 侧用 Redis 维护按 `shop_category_id` 维度的实时值：单子进入休眠延迟计入，延迟处理完成移出。
2. 新管理端工作台按 `shop_category_id` 列表从 barry-inner 查询该值，展示在现有的「真人商品」「低价商品」卡片及其展开的类目明细上。

## 二、范围与不做的事

范围内：
- barry 分发链路的休眠单子集合维护与自愈兜底
- barry-inner 新增按类目列表批量查询的接口
- phoenix suffer（Go）代理该接口
- phoenix 管理端工作台两张卡片的顶部指标 + 类目明细列展示
- 上述链路的准确性验证

不做：
- 不修改分发策略、分发上限规则、延迟队列本身的实现
- 不改动现有 `/barry/workbench-dashboard/*` 既有接口的行为
- **不做历史趋势、留痕与图表**（已确认，只要实时值）
- 不统计 BATCH 分发链路（已确认）
- 不引入新的数据库表

## 三、关键约束（含本轮已确认口径）

1. **计数口径：按「单子当前是否休眠」去重统计**。Redis 用 `SET` 存 assignmentId，`SADD` 进 / `SREM` 出 / `SCARD` 取数。`doDelay` 对已休眠单子的重复投递（`AssignProcessor.java:149`、`:184`）天然不重复计数，也不会重复扣减。
2. **链路范围：只统计非 BATCH 的 `DelayAssignProcessor` 链路**，BATCH 在 `AssignProcessor.java:112` 本就跳过 `doDelay`。
3. **展示形态：卡片顶部指标区 + 展开的类目明细列都要有**。
4. 计数写入挂在分发主链路上，异常需吞掉、不得阻塞或影响分发。
5. 不得引入额外查库：`shopCategoryId` 直接取自 `BaseAssignmentDTO.shopCategoryId`。
6. 休眠标记 `barry_assignment_delay_key_{id}` 是 setEx TTL 自然过期、无显式「处理完成」事件，集合成员必须带 TTL 兜底，避免消息丢失或 `delay.assign.monitor.flag=false` 时永久残留。
7. barry-inner 接口沿用 `WorkbenchDashboardController` 既有的 `shopCategoryIds` 逗号串参数范式。
8. 管理端遵循 phoenix `backend-development`（Handler → Service → Repository）与现有工作台各卡片独立请求、独立渲染的模式。

#### 1. barry 按商品类目维护休眠延迟单子集合（barry-assignment-dbbdfccdb3）
- 目标：在 Redis 维护按 `shop_category_id` 的休眠单子集合，去重反映当前处于休眠延迟中的单子数。

## 六、验收标准（需求级）

1. barry 中单子因达到分发上限进入休眠延迟时，被计入对应 `shop_category_id` 的集合；延迟处理完成后移出。
2. 同一单子重复进入延迟队列不导致数字虚高；消息丢失或消费者关闭不导致数字永久偏高（TTL 兜底）。
3. BATCH 分发链路不计入。
4. barry-inner 提供按 `shopCategoryIds` 列表批量查询的接口，返回逐类目与合计。
5. 新管理端工作台「真人商品」「低价商品」卡片顶部指标与展开的类目明细列，均按各自类目配置展示当前休眠延迟单量，且与 inner 接口返回一致。
6. 全链路不影响现有分发行为与现有工作台指标。
