# 设计过程-01：barry 取单入口接入 uID 在线心跳写入 Redis

## 需求理解

工作台「实时上号」当前按 `order_record` 出单口径统计，只轮询没抢到单的 uID 统计不到。本任务只做**写入侧**：在 barry 统一取单入口把「userId + uID 的最后一次取单时间」写进 Redis ZSET，供后续统计任务（任务 2）按窗口读取。不做查询、不做统计、不加开关、不改 Controller/DTO。

## 勘察到的现状事实

- `barry-business/barry-order-business/barry-order-business-core/.../order/AbsUserOrderService.java:91` 的 `fetchUserOrder` 是唯一统一取单入口；前置校验拦截走 `return buildPreCheckError(...)`，仍在 `try` 内，因此 `finally`（现 148 行起）对「取到单 / 未取到单 / 前置校验拦截」三种情况都会执行，已有 `monitorFetchHit` / `monitorFetchMiss`。
- 只有两个子类：`order/impl/UserOrderServiceImpl.java:32`、`order/impl/UserBatchOrderServiceImpl.java:20`；四个调用方 `TaskController:150`、`OrderController:61`、`BatchTaskController:156`、`FullTaskController:60` 全部经由这两个实现，改抽象类一处即覆盖单条与批量取单。
- `RedisService` 已有 `zadd(String,long,String)`(89)、`expire(String,int)`(279)、`ttl(String)`(289)，无需补能力。
- 参照写法：`order/support/OrderFetchMonitorCache.java`（同目录同类监控缓存的结构与 key 前缀风格）、`FetchAssignmentMonitorCache.expireIfNeeded`(107-111)（`ttl < 0` 才补 TTL 的兜底范例，以及「监控写入失败只 log.warn」的容错约定）。

## 取舍

1. **埋点位置**：放在 `finally` 而不是各 `return` 前。`finally` 天然覆盖前置校验拦截和异常路径，只写一行，也和既有 `monitorFetchHit/Miss` 埋点并列，语义一致。`uuid` 为空时 `record` 内部直接跳过，不需要在调用点判断。
2. **score 单位**：选**秒**（`System.currentTimeMillis() / 1000`）。窗口参数是 `windowSeconds`（默认 120），统计侧 `ZREMRANGEBYSCORE` / `ZCOUNT` 的截止值可以直接 `now - windowSeconds`，不必来回乘 1000。这是与任务 2 的硬契约，已写进代码事实交接。仓库里 `BatchTaskController.recordUserUidUsage` 另有一套毫秒 score 的 `user:uid:zset:*`，是独立的既有机制，本次不复用也不改动。
3. **TTL 策略**：按需求约定，`barry_online_uid_{userId}` 由写入侧 `ttl < 0` 时补 3600 秒兜底（覆盖 key 新建和历史无 TTL 两种情况，且不会每次写入都重置 TTL 触发额外 EXPIRE）；`barry_online_user` 不设 TTL，留给查询侧清理，ZSET 清空后 Redis 自动删 key。
4. **容错**：整个 `record` 方法一层 try-catch + `log.warn`，Redis 抛异常时取单主流程不受影响。没有加开关（需求明确不做）。

## 改动

- 新增 `barry-business/barry-order-business/barry-order-business-core/src/main/java/com/barry/business/order/support/UserOnlineHeartbeatCache.java`：`@Component`，`record(Long userId, String uid)`，`userId` 为空或 `uid` 空白直接返回；`ZADD barry_online_uid_{userId} <秒级时间戳> <uid>` + `expireIfNeeded`，`ZADD barry_online_user <秒级时间戳> <userId>`。
- 修改 `AbsUserOrderService.java`：新增 import 与 `@Autowired UserOnlineHeartbeatCache`（51 行），在 `finally` 首行调用 `userOnlineHeartbeatCache.record(orderRequest.getUserId(), uuid)`。

## 验证

`mvn -o -pl barry-business/barry-order-business/barry-order-business-core -am -DskipTests compile` → BUILD SUCCESS。运行期验收需连 Redis，按需求大纲「心跳写入（任务 1）」五条口径人工验证。

## 遗留风险

- 写路径每次取单多 2 次 ZADD + 至多 1 次 TTL/EXPIRE 往返（TTL 每次都读，只在 `ttl < 0` 时才写 EXPIRE），与既有 `OrderFetchMonitorCache` 的写入量同量级。
- score 单位若与任务 2 理解不一致会导致统计全空，需以本文档与交接要点为准。
