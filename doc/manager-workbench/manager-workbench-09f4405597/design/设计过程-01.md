# 设计过程-01：工作台视觉规范梳理与统一

## 1. 需求怎么理解

需求来源分两层：

- 需求级文档 `doc/requirements/req-1788329024774/需求大纲.md`：本任务是里程碑 `manager-workbench-ui-v1` 下 6 个任务中的第 1 个，是后续任务 2~6（顶部统计卡片、桥接器统计表格、配置抽屉、速度趋势图、加载/空/异常态）的地基任务，**只做规范梳理与落地，不做各区域的深度视觉/交互重排**。需求大纲明确"不做"：不改后端接口/数据结构、不增删卡片、不改配置持久化方式、不引入新 UI/图表库。
- 任务说明（桥接器传入）：真实落点是 `ManagerDashboardPanel.tsx`（4266 行）里的 `manager-data-card`、`manager-stats-grid`、`manager-table` 等公共 class，以及散落的内联 `style`。要求：①盘点现有公共 class 的间距/圆角/阴影/配色；②制定统一视觉规范（卡片间距/圆角/阴影、标题字号字重、状态色、Tooltip 样式）；③落地为可复用样式定义（CSS 变量或统一 class），替换页面中零散的内联 style；④不改业务逻辑/数据结构/交互行为。

两份文档口径一致，没有冲突。任务说明里点名的行号（L1301/1307/1322）与我实际读到的当前文件行号有轻微出入（L1322 当前是纯 `className`，没有内联 style；L1301/1307 确实存在）——这是需求梳理阶段扫描时的文件版本/行号漂移，按代码事实处理，不影响范围判断。

## 2. 勘察到的现状事实

- 目标文件：`phoenix/client/manager/src/app/(console)/manager-dashboard/components/ManagerDashboardPanel.tsx`，4266 行。全文件 `style={{` 出现 **69** 处，`className="manager-*"` 出现 **146** 处。
- 全局样式文件只有一份：`phoenix/client/manager/src/app/globals.css`（约 3900+ 行），管理端所有页面共用，没有 Less/Sass/CSS Modules。
- **这份 globals.css 已经内建了相当完整的设计令牌体系**（`:root` 顶部，约 L3-150）：
  - 品牌色阶 `--manager-primary-*`、中性色阶 `--manager-neutral-*`
  - 语义表面色 `--manager-bg/-surface/-panel/-hover` 等
  - 描边 `--manager-border(-soft/-strong)`
  - 文字色 `--manager-text/-text-soft/-text-faint`
  - 状态色三件套（前景/底色/描边）：`--manager-success(-bg/-border)`、`--manager-warning(-bg/-border)`、`--manager-danger(-bg/-border)`、`--manager-info(-bg/-border)`
  - 圆角尺度 `--manager-radius-xs..xl`
  - 间距尺度 `--manager-space-1..8`（4 的倍数：4/8/12/16/20/24/32）
  - 阴影/高度 `--manager-elevation-1..4`、`--manager-shadow*`
  - 焦点环、动效时长、字体族
- 公共 class 现状（`grep` 定位）：
  - `.manager-data-card`（globals.css:302）：`border-radius:10px; padding:18px; background: var(--manager-surface); border:1px solid var(--manager-border); box-shadow: var(--manager-shadow-soft);` —— 圆角、内边距、阴影已统一，且全部引用变量。
  - `.manager-stats-grid`（globals.css:296）：`display:grid; gap:12px;`，网格列数由页面级 `manager-dashboard-layout` / `manager-dashboard-workload-row` 等修饰类决定（响应式部分留给任务 2）。
  - `.manager-table`（globals.css:1822 起）：表头/表体 padding、边框、hover、选中态、分页、滚动条样式已经系统化，全部使用变量。
  - `.manager-value`（globals.css:1192）：等宽数字字体 + `font-weight:700`，但**原本没有显式 `color`**，导致页面里出现大量 `className="manager-value" style={{ color: "var(--manager-text)" }}` 的冗余覆盖（其实和继承自 `body` 的默认色完全相同）。
  - `.manager-section-label` / `.manager-display-title`：标题字号字重已经有统一定义（12px/700 大写字母间距；700 字重的展示数字），卡片标题体系本身是统一的，只是页面里局部又用内联 `fontSize`/`marginTop` 做二次覆盖（多数是 featured/紧凑态的合理差异化，属于任务 2 的卡片布局范畴）。
  - 状态色三件套变量已存在，但页面里目前没有统一的"状态徽标/Tag"专用 class，状态色使用是直接在 `<Tag color="...">`（AntD 内置色名）或内联 `color: view.accent` 上完成的——这部分和"卡片配色（数据驱动的 accent 色）"绑定在一起，不属于本任务要收敛的"零散内联 style"，予以保留（见第 4 节）。
  - Tooltip：`globals.css` 里没有 `.ant-tooltip` 相关的全局样式覆盖，目前全部是 AntD 默认 Tooltip 外观。页面里 `<Tooltip title="...">` 用法统一（纯文案提示，没有自定义样式），本任务不新增 Tooltip 视觉覆盖，因为现状已经是统一的（AntD 默认即"规范"）。

结论：**卡片间距/圆角/阴影/配色的变量体系已经存在且被 `.manager-data-card`/`.manager-table` 完整复用**，真正的问题不是"缺规范"，而是页面组件里大量重复的内联 `style` 没有收敛到已有的规范上——即需求描述的"大量内联 style、manager-* class 混用"。

## 3. 考虑过哪些方案

### 方案 A：重写 `.manager-data-card` / `.manager-stats-grid` / `.manager-table` 的样式取值

排查后发现这几个 class 的取值（圆角 10px、padding 18px、`var(--manager-shadow-soft)`）本身内部是自洽的，且已经通过变量间接遵循规范。重新定义数值本身不会带来任何收益，反而会引入未经审阅的视觉变化（违反"无视觉回归"验收标准）。**否决**：不是问题所在，改了没有收益还有回归风险。

### 方案 B：把散落的内联 style 逐一改写为"就地内联但统一取值"（不新增 class）

即把 `style={{ color: "var(--manager-text-soft)" }}` 这种写法保留内联形式，只是保证大家都引用同一个 CSS 变量。这确实能保证"配色统一"，但没有解决"内联样式冗余堆砌"本身——验收标准明确要求"无明显内联样式冗余堆砌"，纯内联即使取值统一，仍然是冗余堆砌。**否决**：不满足验收标准里"落地为可复用样式定义"的硬性要求。

### 方案 C：引入一层通用的 Tailwind 风格原子类工具库

即把所有间距/颜色都做成完整的原子类系统（如 `mt-1`~`mt-32`、`text-*` 全套）。收益是以后新代码可以完全不写内联 style。但代价是：①与本项目"Ant Design Token + CSS Modules，不使用 Tailwind"的既定前端规范（`web-development` 技能）冲突；②这是一次性铺开的大改动，超出"任务1"的边界（任务2~6 各自还要深度处理各区域的样式），容易和后续任务的具体设计产生冲突或重复劳动。**否决**：违反项目既有前端规范，且范围过大。

### 方案 D（最终选择）：保留并强化既有的"语义 class + CSS 变量"体系，只新增一组小而精确的复用工具类，定点替换页面中确认为"重复/冗余"的静态内联 style；对由业务数据驱动的动态样式（如 `view.accent`、`featured` 三目运算）保持不变

- 复用维度沿用现有变量：间距优先用 `--manager-space-1/2/3`（4/8/12px，恰好和页面里出现的 4/8/12px 完全对齐），对页面里历史遗留的非 4 倍数间距（6/10/14/18px）新增等值的工具类（不做四舍五入到最近刻度，避免像素级视觉回归），并在 CSS 里加注释说明这是过渡态，后续任务按区域收敛。
- 新增的语义工具类：
  - `.manager-card-icon-lg`：统一卡片图标 `font-size:22px`（原本 14 处完全相同的内联 style）。
  - `.manager-text-soft` / `.manager-text-block` / `.manager-text-strong` / `.manager-text-strong--bold`：对应页面里反复出现的"次要文字色""display:block""主文字色+加粗"三种文字修饰组合。
  - `.manager-card-placeholder`（+`--sm`/`--lg` 修饰符）：统一 loading/空态卡片的"最小高度 + 居中"占位样式（对应任务描述里点名的 L1301/1538）。
  - `.manager-row-between`（+`--align-start` 修饰符）：统一 `<Space>` 里"横向撑满 + 两端对齐"的高频组合。
  - `.manager-card-pad-14` / `.manager-card-pad-18` / `.manager-card-pad-banner`：统一卡片内边距的几种历史取值。
  - `.manager-mt-4/6/8/10/12/14/18`、`.manager-mb-8/12/14/18`：间距工具类，4/8/12 直接引用 `--manager-space-*` 变量，其余保留字面量并在注释里标注为待收敛的历史值。
  - 把 `.manager-value` 补上 `color: var(--manager-text)`（本来就是继承自 `body` 的默认色，属于纯粹的"消除冗余"，无视觉变化），顺带删除页面里 6 处完全等价的内联覆盖。
- 对以下内联 style **明确保留、不做改动**（详见第 4 节），因为它们要么是数据驱动的动态值，要么是单一场景、无重复、改动收益低于风险的取值：`view.background` / `view.accent`（卡片强调色，来自业务配置）、`featured ? ... : ...` 等三目条件样式（卡片紧凑态/展开态的字号级差，属于任务 2 的卡片布局范畴）、`InputNumber`/`Table` 的 `width:"100%"` 等 AntD 表单/表格标准用法、少量真正独此一份的复合样式（如均速卡片值区域的 `display:grid; gap:2`）。

选择方案 D 的判断依据：既满足验收标准（统一规范、消除冗余内联堆砌、可复用样式定义、无视觉回归），又不越界到任务 2~6 的具体区域改造范围，风险最小、改动可审查性最高。

**明确不改动的内联 style**（逐一列出理由）：

- `view.background` / `view.accent` 驱动的 `.manager-dashboard-card__backdrop`、`.manager-dashboard-card__icon` 的 `background`/`color`（6 处）：这是每张卡片各自的强调色（来自 `DASHBOARD_TITLES`/卡片配置生成逻辑），本质是数据而不是样式规范，用 CSS 变量重写只是把同一份内联值挪了个位置，不产生"消除冗余"的收益，且这类卡片强调色的呈现方式属于任务 2（顶部统计卡片视觉）的范畴，留给该任务统一处理更合适。
- `featured ? 28 : 24`、`hasTopRow ? (featured ? 10 : 8) : 0`、`featured ? 8 : 6` 等三目条件样式（L2211/2220）：是同一张卡片组件在"精选/普通"两种布局态下的字号级差，属于卡片自身的响应式/紧凑态设计，改动它需要同时理解任务 2 要落地的响应式方案，本任务不预先决定，避免和任务 2 的设计冲突。
- `InputNumber`/`Table` 的 `style={{width:"100%"}}`（3 处）：AntD 表单控件撑满容器宽度的标准写法，是布局约束不是视觉规范问题，多数 AntD 项目里都是就地内联，改动没有实际收益。
- `minWidth:0`（1 处）：flex 子项防止内容溢出的标准 CSS hack，单一场景无重复，不属于视觉规范范畴。
- 均速卡片值区域 `display:grid;gap:2` + `color:text-soft;fontSize:18`（L3136/3140）：全文件唯一一处这种复合排布，重复度为 1，抽成 class 收益不明显，且该区域是任务 5（速度概览趋势图）职责范围，交给任务 5 一并处理更合理。
- L1740 `AppstoreOutlined` 的 `color+fontSize:18+marginTop:3`：说明性图标的一次性组合写法，唯一场景。
- L1517 `<Text>` 的 `color:"var(--manager-warning)"`：警示色的唯一使用场景（未关联 Bridge 提示），已经在用规范里定义好的 `--manager-warning` 变量，只是没有再抽出一个只服务于这一处的 class；`display:block` 部分已经收敛进 `manager-text-block`。
