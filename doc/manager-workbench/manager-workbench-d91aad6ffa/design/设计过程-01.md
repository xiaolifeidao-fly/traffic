# 设计过程-01：顶部统计卡片网格视觉与响应式优化

## 1. 需求怎么理解

任务说明是本任务唯一需求来源：优化顶部统计卡片网格（`manager-stats-grid`/`manager-dashboard-workload-row`）的排版层次和窄屏表现，落点是 `ManagerDashboardPanel.tsx` L1322-1359（网格容器）、L1853 起 `renderDashboardCard`（L1906/1944 真实工作量分组卡片）、L2395-2477 的 `renderTrendArrow`/`renderTotalPendingMetricValue` 等辅助信息渲染函数。边界：不新增/删除卡片、不改配置抽屉、不改数据字段和取数逻辑。依赖任务1（`manager-workbench-09f4405597`）产出的"语义 class + CSS 变量"样式规范。

## 2. 勘察到的现状事实

- 任务1已经把 `ManagerDashboardPanel.tsx` 里能识别为"重复/冗余"的静态内联 style 收敛为工具类（`manager-text-*`、`manager-mt-*`、`manager-row-between` 等），但明确把顶部卡片网格自身的几处样式（`view.accent`/`background` 强调色、`featured` 三目条件样式）留给本任务处理（见 `doc/manager-workbench/manager-workbench-09f4405597/design/设计过程-01.md` 第 3/4 节"明确不改动"清单）。
- 排查 `renderDashboardCard` 的调用点（`ManagerDashboardPanel.tsx` L1333、L1346）：两处调用都没有传 `featured` 参数，`featured` 默认值为 `false`，且函数里 `if (featured) { return ... }`（L2037）会在到达通用渲染分支（L2170 起）之前就返回。也就是说通用分支里 `featured ? 28 : 24`、`marginTop: featured ? 8 : 6`、`hasTopRow ? (featured ? 10 : 8) : 0` 这几处三目运算里 `featured` 分支永远走不到——是已确认的死分支，不是"数据驱动的动态值"。
- `.manager-dashboard-layout > .manager-dashboard-card`（`globals.css` L2750，两个类选择器，特异度 0,2,0）比 `.manager-dashboard-card--account-status`/`--pending-detection` 等单类选择器（0,1,0）优先级更高，会统一把顶部 9 张卡片的高度钉到 148px，覆盖它们各自声明的 105px。也就是说顶部网格内的卡片实际已经是等高的，`align-items: stretch` 不会造成参差不齐——网格本身没有明显的错位问题。
- 顶部网格断点（`globals.css` L3625-3654）已经是 ≤1440px→4 列、≤1100px→3 列、≤820px→2 列、≤560px→1 列，恰好覆盖验收里点名的 1440/1920/1280（1280 落在 1100~1440 区间，走 4 列）三个宽度，不需要新增断点。
- 真正暴露的问题：①卡片主数值（`.manager-display-title`，L2217 一带）和"真实工作量"卡片的数值（`.manager-dashboard-card__real-workload-value`，L1922/1962 一带）都没有溢出保护，窄列下长数字只能靠外层 `.manager-dashboard-card { overflow: hidden }` 硬裁切，观感生硬。②`renderTotalPendingMetricValue`（L2404）、`renderDelayDetectionMetricValue`（L2428）里"昨日剩余""延迟率"这类括注辅助信息复用了 `.manager-dashboard-card__metric-note`，该类此前直接继承父级 `.manager-dashboard-card__metric-value` 的等宽字体+加粗，同时把颜色设成 `var(--manager-warning)`（橙色）——和真正表示告警的 `.manager-dashboard-card__metric-value--pending` 撞色、撞视觉权重，辅助信息和主数值抢焦点。

## 3. 方案怎么落到改动（未出现需要取舍的方案分歧，改动均为等价简化/局部新增，未单列候选方案对比）

### 3.1 `ManagerDashboardPanel.tsx`

- L2211/2214/2217-2223：通用卡片分支里，把已确认死掉的 `featured` 三目去掉（等价于直接取 `false` 分支的字面值），套用任务1建立的工具类：
  - `<Space style={{width:"100%",justifyContent:"space-between",marginTop:...}}>` → `className={`manager-row-between${hasTopRow ? " manager-mt-8" : ""}`}`（复用任务1已有的 `manager-row-between`/`manager-mt-8`，不新增小众工具类）。
  - 标题 `style={{letterSpacing:"0.12em"}}` → 新增 `manager-dashboard-card__title-label`（这是卡片标题特有的字间距，不属于全局工具类范畴，跟随本任务落在组件自身的 BEM 类里）。
  - 主数值 `style={{fontSize:featured?28:24, marginTop:featured?8:6}}` → 新增 `manager-dashboard-card__value`（同上，卡片自身的字号/间距，值与原 `featured=false` 分支逐一核对一致，零视觉变化）。
- 其余部分（`view.accent`/`view.background` 驱动的强调色、`featured===true` 分支本身、`minWidth:0` 等）按任务1记录的理由维持不动：强调色是每张卡片各自的数据值，不是重复样式；`featured` 分支目前没有任何调用方传 `true`，属于预留但未激活的能力，本任务边界内不做主动删除或改造，避免在没有可见调用场景的情况下引入未经验证的改动。

### 3.2 `globals.css`

- 新增 `.manager-dashboard-card__title-label { letter-spacing: 0.12em; }`、`.manager-dashboard-card__value { margin-top:6px; font-size:24px; max-width:100%; overflow:hidden; text-overflow:ellipsis; white-space:nowrap; }`：字号/间距和原内联值完全一致，新增的溢出保护是本任务对"窄屏不错位、不溢出"验收标准的直接补强。
- `.manager-dashboard-card__real-workload-value` 及其 `> div` 补充 `max-width:100%; overflow:hidden` / `overflow:hidden; text-overflow:ellipsis`：真实工作量分组卡片（L1906/1944 对应的两个 `manager-dashboard-card__real-workload-group`）在 820px 断点下会退到较窄的两列，25px 等宽大字号数值原来只有 `white-space:nowrap` 没有省略号，窄屏下会被父级 `overflow:hidden` 硬切。
- `.manager-dashboard-card__metric-note`（`renderTotalPendingMetricValue`/`renderDelayDetectionMetricValue` 用到的括注辅助信息）颜色从 `var(--manager-warning)` 改为 `var(--manager-text-faint)`，并显式声明 `font-size:12px; font-weight:500`（不再继承父级等宽加粗），让"昨日剩余""延迟率"这类辅助数字明显弱于主数值和真正的告警态（`--metric-value--pending` 的橙色），落实"主数值/辅助信息视觉权重区分"的验收要求。`renderTrendArrow` 的箭头本身字号已是 10px、颜色随涨跌走 `--primary-deep`/`--danger`，本来就是全站统一的最小辅助元素，排查后未发现需要改动的地方。

### 3.3 未改动、且说明理由

- 网格断点结构（`globals.css` L3625-3654）：已覆盖验收要求的 1440/1920/1280 三个宽度，且顶部网格的等高问题已经被既有的 `.manager-dashboard-layout > .manager-dashboard-card` 规则处理，未发现需要新增断点或改列数的证据。
- `view.background`/`view.accent` 驱动的卡片强调色（背景渐变、图标底色）：延续任务1的判断——这是每张卡片各自的数据值，不是重复堆砌的样式，用 CSS 变量重写只是把同一份内联值挪位置，没有消除冗余的收益，反而在没有强烈动机的情况下增加了回归面，本任务不做改造。
- `manager-dashboard-workload-row`（真实工作量两卡）网格列数在 ≤820px 才收到 2 列（本来就是 2 列，等于没变化）、≤560px 收到 1 列：实测其内部各级 grid 都已用 `minmax(0,1fr)` + `min-width:0`，未发现新增断点的必要性。

## 4. 验证

- `npx tsc --noEmit -p tsconfig.json`（`phoenix/client/manager` 目录）：**通过**，无类型错误。
- `globals.css` 大括号计数：707 / 707，配对正确。
- 逐处 diff 走查：确认所有 JSX 改动都是"内联 style 字面值 → 等值 class"（`featured` 分支值锁定后与原代码逐一核对一致）或"新增溢出保护/降低辅助信息视觉权重"的纯增量，没有引入其它数值变化。
- 浏览器实际走查：尝试过 `npm run dev` 起本地 Next.js 服务，但 `/`、`/manager-dashboard` 均返回 404（该管理端页面依赖 Electron 主进程注入的鉴权/RPC 环境，脱离 Electron 壳单独用浏览器访问不可用），与任务1记录的限制一致，本轮同样未能做浏览器级视觉走查。已尽量通过精确的选择器特异度分析和数值核对代替直接观察。

## 5. 遗留与风险

- 未做浏览器实际渲染验证，建议测试阶段在真实管理端环境里核对：①顶部 9 张卡片在 1920/1440/1280 三档宽度下主数值不再硬裁切（长数字改为省略号）；②"昨日剩余""延迟率"括注文字明显比主数值和橙色告警态弱；③真实工作量卡片（真人实际完成/低价实际完成）在收缩到两列时数值不溢出。
- `featured===true` 分支（L2037-2094）目前没有任何调用方激活，本任务未清理，如果后续任务需要启用"精选卡片"外观，需要重新评估其响应式表现（该分支的 `grid-template-columns: minmax(280px,...) minmax(280px,...) auto` 在窄屏下未做验证）。
