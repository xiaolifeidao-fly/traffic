# 设计过程-01：实时上号改用 Redis 心跳口径并切换 /user-online-overview

任务键：manager-workbench-a4d1e4d957 ｜ 需求：req-1788421430587 ｜ 前置：barry-assignment-6adff9a954（心跳写入，已完成）

## 一、需求理解

前置任务已在取单入口 `AbsUserOrderService.fetchUserOrder` 的 `finally` 写入 uID 心跳，落到两个 ZSET：
`barry_online_uid_{userId}`（member = uid）与 `barry_online_user`（member = userId），score 为**秒级** Unix 时间戳。
本轮只做读侧：把工作台「实时上号」的 online 三字段（`onlineUserCount` / `onlineAccountCount` / `detailList`）
从 `order_record` 的出单口径换成 Redis 心跳口径，并且只切 `/user-online-overview`；`/user-overview` 与
`OrderRecordRepository.summarizeWorkbenchOnlineUsers` 原样保留给 Kakrolot 等既有调用方。DTO 字段结构不变，
所以 phoenix 与前端零改动。

## 二、勘察到的现状事实

- `WorkbenchDashboardServiceImpl.userOverview`（`barry-service/barry-order-service/barry-order-service-core/.../service/order/WorkbenchDashboardServiceImpl.java:111-129`）先查当日 `userCount` / `accountCount`，再用 `summarizeWorkbenchOnlineUsers(startTime)` 填 online 三字段；窗口常量 `DEFAULT_USER_OVERVIEW_WINDOW_SECONDS = 120`（:67），窗口校验 `statisticsWindowSeconds`（1..3600）。
- `WorkbenchDashboardController`（`barry-gateway/barry-gateway-inner-client/.../controller/workbench/WorkbenchDashboardController.java`）里 `/user-overview`(:40) 与 `/user-online-overview`(:48) 改造前都调 `userOverview`。
- `RedisService` 已有 `zadd`、带 offset/count 的 `zRangeByScore`、`getZCard`、`eval`，缺 `zcount`、`zremrangeByScore` 和无 offset 的 `zRangeByScore`。
- `barry-order-service-core` 的 pom 已依赖 `barry-user-service-api`（`UserService.findByIds(List<Long>)` 返回 `List<UserDTO>`，含 `id/username/channel`），同模块的 `ManualTaskStatisticsServiceImpl:54` 已在注入它，注入方式照抄即可。
- Bean 注册走 `spring/spring-barry-service-order.xml` 的 `component-scan base-package="com.barry.service.order"`，新建 `support` 子包能被自动扫到，不需要额外配置。

## 三、候选方案与取舍

**在线计数怎么拿**（N 个用户各一个 ZSET）：

1. 逐用户 `ZCOUNT` —— 实现最直白，但 N 次网络往返，数千在线用户时读路径直接被拖垮；否决。
2. Pipeline —— `RedisService` 目前没暴露 pipeline 能力，为此再加一层封装超出本任务范围；否决。
3. **Lua 批量（选中）** —— 现成的 `eval` 就能一次往返处理一批 key：脚本内对每个 KEYS 先 `ZREMRANGEBYSCORE` 清掉滑出窗口的 uID，再 `ZCOUNT` 取窗口内计数，返回计数数组。分批 500 个 key，避免单条命令 key 数过大。顺带在读的时候完成了 uID 维度的清理，写侧的 TTL 兜底只兜彻底离线的用户。

**统计组件放哪一层**：写侧的 `UserOnlineHeartbeatCache` 在 `barry-business/barry-order-business-core`，但 business 在 service 之上，`WorkbenchDashboardServiceImpl` 不能反向依赖它。故读侧新建独立组件放在 `com.barry.service.order.support`，与 `com.barry.service.assignment.support.FetchAssignmentMonitorCache` 的分层惯例一致；key 常量在两侧各自声明，靠需求文档的 key 契约保证一致（跨层共享常量需要新建公共模块，代价大于收益）。

**接口怎么切**：不在 `userOverview` 里加分支或开关（需求明确不加开关），而是**新增** `userOnlineOverview` 方法，controller 的 `/user-online-overview` 改指向它。`/user-overview` 的调用链一行没动，逐字段不变是结构上保证的，不依赖回归测试去证。

## 四、方案落到的改动

1. `RedisService`：补 `zRangeByScore(key,min,max)`、`zcount(key,min,max)`、`zremrangeByScore(key,min,max)` 三个方法，写法与相邻方法完全一致（`getJedis()` / `finally closeJedis`）。`Double.NEGATIVE_INFINITY` / `POSITIVE_INFINITY` 由 jedis 自己转成 `-inf` / `+inf`。
2. 新增 `UserOnlineStatisticCache.onlineUidCounts(int windowSeconds)`：
   - `threshold = now秒 - windowSeconds`（**不乘 1000**，与写侧秒级 score 对齐）；
   - `ZREMRANGEBYSCORE barry_online_user -inf threshold` 清窗口外用户（该 key 无 TTL，清空后 Redis 自动删 key，`ZCARD` 不会无限增长）；
   - `ZRANGEBYSCORE barry_online_user threshold +inf` 取在线 userId；
   - 分批 500 走 Lua 拿计数，计数为 0 的用户直接不进结果（对应验收里「0 值过滤」）；
   - 整体 try-catch，Redis 异常时 `log.warn` + 返回空 Map，工作台其它卡片不受影响。
   - 清理用的上界与计数用的下界都取 `threshold`，边界项已被删除，两处不会重复计入。
3. `WorkbenchDashboardService` 接口新增 `userOnlineOverview`；`WorkbenchDashboardServiceImpl` 实现：`userCount`/`accountCount` 仍走 `orderSumRecordRepository`，online 三字段来自 Redis，明细用 `userService.findByIds` 批量补 `username`/`channel`（查不到时填空串，与旧 SQL 的 `COALESCE(...,'')` 行为一致），最后按账号数倒序 + userId 升序排序，与旧 SQL 的 `ORDER BY` 一致。
4. Controller `/user-online-overview` 改调 `userOnlineOverview`，其余端点不动。

## 五、验证与遗留风险

- 验证：`mvn -o -DskipTests -pl barry-jedis,order-service-api,order-service-core,inner-client -am install` 编译通过，产物 class 已生成。运行期行为需要联调 Redis 验证（见交付说明的测试交接）。
- 遗留：需求提到在线用户到万级时要加 5-10 秒结果短缓存。本轮没加，但计数逻辑收敛在 `UserOnlineStatisticCache.onlineUidCounts` 单个方法里，加缓存只需包一层，不用改 service。
- 既定行为：轮询间隔超过 120 秒的 uID 会滑出统计，属预期口径。
- Redis 重启/清库后窗口内数据短暂偏低，属可接受范围。
